# Подключение React-интерфейса к ARTA API

Сейчас используется `demoRepository` в `src/lib/store.js`. Расчёты из `src/lib/domain.js` предназначены только для локальной симуляции; сервер должен оставаться источником истины для остатков, денег, прав и аналитики.

Контракты: `../docs/api.md`, `../docs/ai-schema.md`; фактические схемы: `../backend/app/schemas/`. В актуальной `main`, от которой создана ветка `landing`, уже есть маршруты auth, organizations, materials, commerce, planning и analytics. React-интерфейс пока не подключён ни к одному из них. Наличие маршрутов в коде не подтверждает запуск сервера или настройку внешних сервисов; перед интеграцией сверить контракты и окружение.

## Последовательность

1. Ввести явные режимы `demo/api` и URL API. Не подставлять demo при ошибке сервера.
2. Подключить регистрацию/вход, токен и текущую организацию. Разделить действия продавца и покупателя; сервер повторно проверяет роль и владение.
3. Загружать `/materials` с серверной пагинацией и фильтрами. Отображать серверный `available_kg`, не вычислять его из локальных заявок.
4. Создавать черновик через POST `/materials`, затем загружать фото multipart в `/materials/{id}/images`, подтверждать актуальную `version` и публиковать. Не отправлять data URL в API.
5. Подключить `/ai/analyze` и опрос статуса. Предложения ИИ и подтверждённые человеком поля остаются разными сущностями.
6. Создавать `/reservations` с идемпотентностью. Демо позволяет сыграть обе роли; в реальном режиме действия зависят от авторизованного участника.
7. Получать метрики из `/analytics/summary`. Использование подтверждать отдельно через `/transactions/{id}/reuse-confirmation`.

## Отличия демонстрационной модели

- `total_kg`, `quantity_kg`, `price_per_kg` — decimal-строки.
- `material_type` и `condition` используют значения серверных enum; UI содержит подмножество типов материалов.
- `image` — локальный URL/data URL; API использует `images`, метаданные и разрешённые временные ссылки.
- `description`, `organization_name`, `is_own` — поля демо-интерфейса. Не пересылать их в строгий DTO создания материала без сверки контракта.
- Демо-ID нельзя отправлять в API.
- `received` соответствует завершению получения (`completed` в контракте). `reused` отображает отдельный impact-факт, а не новый серверный статус reservation.
- Подтверждение использования всей полученной массы — упрощение демо. Частичное использование должно следовать API.
- Сумма в форме — предварительный расчёт. Реальные суммы, остатки и цены берутся с сервера.
- Нужны состояния 401/403/404/409/422/429, сетевых ошибок и загрузки. Блокировка кнопки не заменяет серверную идемпотентность.

## Публикация

`npm run build` создаёт статический `dist/`. BrowserRouter требует SPA rewrite на `index.html` для `/catalog`, `/create`, `/requests`, карточек и четырёх маршрутов аккаунта. Публикация и push в этой задаче не выполнялись.

## Готовые экраны аккаунта

`src/pages/Auth.jsx` содержит `/register`, `/login`, `/forgot-password`, `/reset-password`. Обработчики проверяют поля и показывают короткое сообщение о недоступности соответствующего действия. Плашки деморежима убраны по запросу владельца; запросов и авторизованной сессии по-прежнему нет. Пароли не сохраняются в localStorage, sessionStorage, URL или логах.

Регистрация разделена по роли. Контракт продавца согласован с `backend/app/schemas/auth.py` и `organization.py`; для личного профиля покупателя требуется изменение backend:

- Роли `enterprise` (предлагает ткань) и `buyer` (ищет материал); регистрация администратора не предусмотрена.
- Продавец (`enterprise`): `organization` с `name`, `city`, `activity_type`, необязательным `contacts.contact_name`.
- Покупатель (`buyer`): только имя и город. Предлагаемый DTO — `{ email, password, role: "buyer", profile: { name, city } }`. В текущем backend `organization` обязательна для обеих ролей: **не отправлять buyer DTO до обновления серверной схемы и модели профиля**. Не создавать фиктивную организацию для обхода этого ограничения.
- `activity_type`: `garment_factory`, `workshop`, `recycler`, `other`.
- Email проверяется; новый пароль — 10–128 символов. Подтверждение пароля остаётся в интерфейсе.
- `validateRegistrationProfile(values)` проверяет только поля выбранной роли. `registrationPayload(values)` подготавливает соответствующий DTO после успешной валидации; скрытые поля другой роли исключены. Email нормализуется, пароль не обрезается и не преобразуется. Сейчас функция не отправляет и не хранит данные.

При подключении заменить локальное завершение формы на вызов сервера: `POST /auth/register` возвращает пользователя с организацией, **не токен**. Вход выполняется отдельно через `POST /auth/login` с `{ email, password }`. Показывать успешную регистрацию или вход и открывать личный кабинет только после подтверждённого ответа сервера; добавить ожидание, серверные ошибки и повторную отправку после ошибки. Выбранная в форме роль не предоставляет разрешения — права проверяет backend.

В текущем backend нет маршрутов восстановления и смены пароля. Для них нужны серверный контракт и одноразовый токен из письма, обработка истёкшей/использованной ссылки и одинаковый внешний ответ для существующего и неизвестного email. `/reset-password` пока открывает только дизайн формы, без изменения аккаунта.
