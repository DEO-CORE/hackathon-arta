# React-интерфейс и единый ARTA API

`landing/` и Flutter-клиент используют один бэкенд в `backend/`. Архитектура — слоистый монолит: HTTP-маршруты → сервисы → SQLAlchemy/PostgreSQL. Новый сервер отдельно создавать не нужно.

## Запуск

Сначала запустите PostgreSQL и API по [инструкции backend](../backend/README.md). Для существующей базы обязательно выполните `alembic upgrade head`: миграция `4992ea002f67` добавляет личных покупателей, описание партии и токены восстановления. Она сохраняет существующие организации и пользователей. Обратная миграция требует отсутствия личных покупателей: прежняя схема не умеет их хранить.

Затем в другом терминале:

```sh
cd landing
npm ci
cp .env.example .env
npm run dev -- --port 5173 --strictPort
```

Откройте `http://127.0.0.1:5173`. Vite перенаправляет `/api/*` на `http://127.0.0.1:8000/*`. Для другого API задайте `API_PROXY_TARGET` при запуске Vite. Если порт занят, выберите другой и добавьте его origin в `backend/.env` → `CORS_ORIGINS`. `LANDING_URL` должен совпадать с адресом сайта для восстановления пароля.

## Режимы

- `VITE_DATA_MODE=api` — режим по умолчанию, все операции проходят через сервер.
- `VITE_DATA_MODE=demo` — отдельная локальная демонстрация, явно отмеченная в интерфейсе; данные браузера не пересылаются в API.
- `VITE_API_URL=/api` — адрес API относительно сайта. Переменные `VITE_*` публичны: ключ OpenAI и SMTP-пароль сюда не помещать.

При отказе сервера интерфейс показывает ошибку, а не подставляет демоданные. `src/lib/api.js` отвечает за HTTP; `store.js` — за сессию и серверные данные; `demo-store.js` — за изолированную демонстрацию. Остатки, права, итоговые суммы и подтверждённое использование рассчитывает сервер.

## Авторизация и восстановление

| Действие | Маршрут |
| --- | --- |
| Регистрация | `POST /auth/register` |
| Вход сайта | `POST /auth/session` |
| Текущий пользователь | `GET /auth/me` |
| Выход | `DELETE /auth/session` |
| Запрос письма | `POST /auth/forgot-password` |
| Новый пароль | `POST /auth/reset-password` |

Регистрация возвращает пользователя, а не токен. После неё нужно войти. Продавец передаёт `organization`, личный покупатель — `profile: {name, city}` и `role: buyer`. У личного покупателя `organization` и `organization_id` равны `null`; его заявки и потребности связаны с `user_id`. Старые покупатели-организации продолжают работать.

Сайт использует HttpOnly-cookie `arta_session`; токен не сохраняется в localStorage. Изменяющие запросы с cookie проверяют `Origin`. Flutter сохраняет прежний `POST /auth/login` и Bearer-токен. В production cookie требует HTTPS (`Secure`); публикуйте сайт и API под одним origin через `/api`.

Для почты заполните `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, при необходимости `SMTP_USERNAME` и `SMTP_PASSWORD`. `SMTP_SECURITY=starttls` обычно соответствует 587, `ssl` — 465; `none` предназначен для локального тестового сервера. Адрес в письме берётся из `LANDING_URL`.

Ответ на запрос восстановления одинаков для известного и неизвестного email. Ссылка действует `RESET_TOKEN_MINUTES` минут, одноразовая; в БД хранится хеш токена. Токен передаётся во фрагменте URL (`#token=...`), который форма убирает после чтения. Смена пароля отзывает предыдущие сессии и остальные ссылки. Без SMTP сервер явно возвращает 503. Письмо отправляется фоновой задачей; ошибки доставки фиксируются в журнале сервера без пароля и токена. Гарантированной очереди доставки в этой версии нет.

## Каталог, публикация и AI

Гостям доступны `GET /public/materials`, `/public/materials/{id}`, `/public/material-cities` и `/public/statistics`. Каталог использует серверные фильтры и пагинацию. Фото выдаются по подписанным ссылкам на 5 минут; черновики и контакты гостям не доступны.

Публикация: `POST /materials` → multipart `POST /materials/{id}/images` → `POST /materials/{id}/confirm` с текущей версией → `/publish`. Файл отправляется как файл, не как data URL. Состав и характеристики подтверждает человек.

Для реального анализа в **backend/.env**:

```dotenv
VISION_PROVIDER=openai
VISION_MODEL=имя_доступной_модели_с_vision_и_structured_outputs
VISION_API_KEY=ваш_ключ
DEMO_MODE=false
```

После изменения перезапустите API. Провайдер обращается к OpenAI Chat Completions с фотографиями и строгой JSON-схемой; результаты проверяются Pydantic. Кнопка анализа создаёт `/ai/analyze`, затем опрашивает `/ai/analyses/{id}`. Предложения AI показаны отдельно от подтверждённых характеристик; изменение партии делает результат устаревшим. Сбой или отсутствие ключа не заменяется подготовленным ответом. В разработке `VISION_PROVIDER=disabled` позволяет работать вручную.

## Заявки и учёт

`POST /reservations` создаёт заявку. `PATCH /reservations/{id}` принимает `confirm`, `cancel`, `transfer`, `complete`. Продавец резервирует и передаёт, покупатель подтверждает получение. Каждое изменение повторно проверяет роль и принадлежность на сервере. Отмена разрешена до передачи; частичная передача освобождает разницу. Операции передаются с `Idempotency-Key`, чтобы сетевой повтор не списывал массу дважды.

Завершённая передача ещё не означает использование. Для него нужен `POST /transactions/{id}/reuse-confirmation` с фактической массой и основанием; разрешено частичное использование. UI-статус `received` соответствует серверному `completed`; `reused` означает, что вся полученная масса отдельно подтверждена как использованная. Это не дополнительный статус заявки в базе.

Личные показатели загружаются из `/analytics/summary`. Публичный счётчик `/public/statistics` суммирует подтверждённые записи использования, включая внутреннее использование. Денежные значения и масса в API — decimal-строки; итоговая сумма берётся из сделки, предварительная сумма заявки — из серверного `requested_sale_amount_kgs`.

## Проверки и публикация

```sh
npm test
npm run build
```

Браузерный тест `tests/e2e/live-api.spec.js` проверяет реальную регистрацию, cookie, загрузку фото, публикацию, резерв, частичную передачу, получение и использование. Запускайте его **только с отдельной тестовой БД**: он создаёт аккаунты и сделку. Например, API на 8001 с тестовой `DATABASE_URL`, Vite на 5174 с `API_PROXY_TARGET=http://127.0.0.1:8001`:

```sh
npx playwright install chromium
PLAYWRIGHT_BASE_URL=http://127.0.0.1:5174 npm run test:e2e
```

Для установленного Chromium можно задать `PLAYWRIGHT_CHROMIUM_PATH`. Старые демонстрационные проверки доступны через `PLAYWRIGHT_MODE=demo`; они предназначены для локальных сценариев, а не подтверждения интеграции API.

`npm run build` создаёт `dist/`. На хостинге настройте SPA rewrite на `index.html` и reverse proxy `/api` к бэкенду со снятием префикса. Vite proxy работает только при разработке. Секреты остаются на сервере. Запускайте один процесс API; фотографии требуют постоянного диска и резервного копирования. Публикация, push и реальные обращения к OpenAI/SMTP без настроек не выполнялись.
