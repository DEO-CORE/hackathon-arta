## 1. Факты о реализации

- `VISION_PROVIDER`: `disabled` (по умолчанию) / `mock` / `http_json` (`config.py`).
- `mock` допустим только при `DEMO_MODE=true`; иначе ошибка конфигурации. В production требуется `http_json` и `DEMO_MODE=false`; `DEMO_MODE` несовместим с production.
- `http_json` требует `VISION_ENDPOINT` (только `https://`), `VISION_MODEL`, `VISION_API_KEY`; таймаут `VISION_TIMEOUT_SECONDS` (1..20 с).
- Адаптер `http_json` - это НЕ клиент конкретного вендора (не OpenAI/Gemini/Claude). Он делает `POST` на указанный шлюз с телом `{model, images[base64], schema, instruction}` и Bearer-ключом и ожидает на выходе JSON по нашей схеме. Это договорной формат: реальный вендор должен стоять за шлюзом, который его реализует. Такого шлюза в репозитории нет.
- Mock-провайдер возвращает один и тот же файл фикстуры (`app/fixtures/demo-analysis.json`) для любого фото. Он не анализирует изображение.
- BLK-02 (выбор провайдера и ключ) в `TASK_BOARD.md` имеет статус `blocked`; AI-03 (живой адаптер, один реальный прогон) - `todo`. Записи о выборе провайдера в `docs/decisions.md` нет.
- Тестов на ветку `http_json` нет: поиск `respx`, `MockTransport`, `call_provider`, `INVALID_PROVIDER_RESPONSE` в `backend/tests` пуст.

## 3. Формулировки для питча

Можно говорить:
- a: «ИИ-анализ предлагает по фото визуальные признаки: цвет, рисунок, видимую фактуру, и варианты применения. Это предложение, не измерение.» Только если демо показано в режиме «Симуляция» - сказать об этом вслух: «в демо - смоделированный ответ».
- b: «Состав по фото мы не определяем: это невозможно. Состав вводит человек, неизвестный остаётся неизвестным.»
- c: «Публикация партии невозможна без подтверждения характеристик человеком; ИИ ничего не подтверждает сам, а устаревший анализ не может подтвердить изменённую партию.»
- d: «Ответ модели проверяется по строгой схеме; невалидный ответ сохраняется как ошибка, не как результат.» (реализовано; одна оговорка - см. разрыв ниже.)
- e: «Анализ идёт в фоне, клиент опрашивает статус; сбой ИИ не блокирует каталог и ручной ввод.» Не называть «очередью».
- f: «Адаптер к внешнему vision-API реализован и настраивается через конфигурацию; боевой прогон с реальным провайдером ещё не выполнен.»
- g: «ИИ предлагает признаки; совместимость считают правила, распределение - математический solver; остатками ИИ не управляет.»
- h: «Демо-режим явно помечен как симуляция в API и в интерфейсе.»
- i: «Оценки точности пока нет; это следующий шаг после получения доступа к провайдеру.»

Нельзя говорить:
- «ИИ определяет состав / процент хлопка / вес / прочность / безопасность».
- «ИИ определяет тип ткани и переплетение» (есть только «на вид трикотажное / тканое»).
- «Живой ИИ подключён и протестирован», «работает на реальном провайдере», «интегрирован с OpenAI/Gemini/Claude» (вендор не выбран).
- «Точность N%», «высокая точность», «обучили модель», «собственная модель».
- «Каждый результат ИИ проверяет человек» (подтверждение возможно без анализа).
- «Надёжная очередь задач».
- Показывать фикстуру как результат анализа загруженного фото без плашки «Симуляция».
- Любые CO2, цены, спрос как выход ИИ (в схеме и промпте их нет).

## 4. Главный разрыв, который может вскрыть жюри

Жюри попросит загрузить новое фото и увидеть реальный анализ: сейчас любое фото в демо даёт одну и ту же фикстуру, а реальный провайдер ни разу не запускался (BLK-02).
Исправление одним предложением: выбрать вендора, задать `VISION_ENDPOINT/MODEL/API_KEY`, один раз прогнать реальное синтетическое фото через `http_json` с записью результата и добавить тест адаптера на подменённом HTTP-транспорте (валидный ответ, битый JSON, таймаут, 429), иначе в питче говорить только «симуляция».
