# Навигация по ролям

Статус: черновик на утверждение. Только планирование: код и API не меняются. Текст интерфейса русский, идентификаторы английские. Любое скрытие или блокировка элемента в интерфейсе удобство; права, владение и остатки проверяет сервер на каждом запросе (CLAUDE.md §4, `docs/api.md` §5).

Источники: `visual-system.md` (§5.11 про навигацию заменён пунктом 4.2 плана), `visual-screens.md` (S01-S06), `arta-ui-redesign-plan.md` (§4.2 навигация, §4.3 компоненты), `reference-analysis.md` (паттерны 5, 6, 7, 10), референсы в `docs/design/referance/` (`home.png`, `bottom_navigation.png`, `success and other.png`, `extra-2.png`). Код: `frontend/lib/app/router.dart`, `frontend/lib/app/tab_shell.dart`, `frontend/lib/features/home/presentation/home_screen.dart`, `frontend/lib/features/auth/models/auth_models.dart`. Чужой дизайн не копируется: референсы дают только приёмы (плавающая панель, подпись у иконки, стат-плашки), без их контента, цветов лайма и логотипов.

## 0. Соответствие названий

| Название в задаче | Роль в API / коде | Примечание |
| --- | --- | --- |
| SUPPLIER | `enterprise` (`UserRole.enterprise`), тип деятельности `garment_factory` | В коде и API слова SUPPLIER нет. Подпись в интерфейсе: «Предприятие». |
| BUYER | `buyer`, тип `workshop` | Подпись: «Мастерская» / «Покупатель». |
| RECYCLER | `buyer` с `activity_type = recycler` | Отдельной роли в API нет (CLAUDE.md §4). Отличается только типом деятельности. |
| ADMIN | `admin` | Не назначается через API; создаётся серверной консолью (`docs/api.md` §22). |

Следствие: навигацию строит клиент из пары (`role`, `activity_type`), но источник истины - сервер. Если клиент ошибся, сервер вернёт 403.

## 1. Карта по ролям

Общий принцип: до трёх вкладок плюс то, что уже существует. Вкладка для экрана, которого ещё нет, не показывается (план §4.2, решение 0). Ниже «Сейчас» - что есть в коде, «Цель» - после реализации экранов из CLAUDE.md §14.

Каждая вкладка: иконка плюс видимая подпись (утверждено). Активная вкладка объявляется скринридеру как «выбрано».

| Роль | Нижняя навигация, порядок (подписи) |
| --- | --- |
| SUPPLIER (`enterprise`) | Сейчас: Главная, Партии, Организация. Цель: Главная, Партии, Сделки, Организация. |
| BUYER (`buyer`, мастерская) | Сейчас: Главная, Каталог, Организация. Цель: Главная, Каталог, Заявки, Организация (потребности открываются со вкладки «Заявки» отдельным разделом «Мои потребности»). |
| RECYCLER (`buyer` + `recycler`) | Те же вкладки, что у BUYER; различаются тексты и фильтры по умолчанию (п. 2.3). Отдельных вкладок нет. |
| ADMIN | Нижней навигации нет. Отдельный вход в веб-панель `/admin` (п. 5). В приложении ARTA для роли `admin` не показывается ничего. |

Вкладка «Аналитика» не вводится отдельно: в первой версии это блок на «Главной» (п. 2). Отдельная вкладка появляется, когда есть три и более самостоятельных экрана аналитики (решение для владельца 3).

Широкий экран (600 dp и шире): та же четвёрка пунктов слева в рейле (`AppShell` уже выбирает рейл или плавающую панель). Порядок и подписи те же.

Скрыта нижняя панель на: `/login`, `/register`, `/verify-email`, `/materials/new`, `/materials/:id`, `/materials/:id/edit`, `/materials/:id/analysis` (снизу закреплённое главное действие). Это уже так в коде: `AppTabShell` оборачивает только вкладочные экраны.

## 2. Главный экран по ролям (блоки сверху вниз)

Общий каркас (реализован): верхняя строка (чип организации с аватаром, названием и ролью, кнопка «Меню»), двухтоновое приветствие «Здравствуйте, {организация}», карточка «Следующий шаг», блок партий. Метрики на главной показываются только для значений, которые возвращает `GET /analytics/summary`; пока он не подключён, их нет, нулей-заглушек тоже нет (`dashboard.md`).

### 2.1 SUPPLIER (`enterprise`)

1. Демо-баннер (если демо-режим).
2. Верхняя строка: чип организации «Название / Роль: Предприятие», кнопка «Меню».
3. Приветствие.
4. Карточка «Следующий шаг»: сначала черновик с невыполненными пунктами публикации, иначе последняя партия (реализовано, `nextStepItem`). Цель: приоритет по данным API: черновик без подтверждения, затем заявка в статусе pending («Заявка ждёт ответа»), затем подтверждённая заявка, ожидающая передачи.
5. Стат-плашки «Свободно / Зарезервировано / Передано» - только по `analytics/summary`, каждая с подписью вида значения (зарегистрировано, распределено, факт). Прогноз плана отдельной плашкой с меткой «Ожидается». [Цель]
6. Блок «Ваши партии» (горизонтальная лента, до 10, реализовано) со ссылкой «Все» на «Партии».
7. Главное действие: «Создать партию» (в карточке при пустом списке - реализовано; в заголовке вкладки «Партии» - цель).

### 2.2 BUYER (`buyer`, мастерская)

1. Баннер, верхняя строка (роль: «Покупатель»), приветствие.
2. Карточка «Следующий шаг» (цель): активная заявка по статусу: «Заявка подтверждена, ждёт передачи», «Передано - подтвердите получение». Если заявок нет - «Открыть каталог» (реализовано в пустом состоянии).
3. Блок «Подходящие партии» - лента опубликованных партий (сейчас блок называется «Ваши партии» и показывает каталог; для покупателя заголовок должен быть «Доступные партии», это правка копии, не новая функция).
4. Блок «Мои потребности» (цель): одна строка-ссылка и счётчик активных потребностей из `GET /buyer-requirements`.
5. Главное действие: «Открыть каталог».

### 2.3 RECYCLER (`buyer` + `recycler`)

Каркас как у BUYER. Отличия только в данных и копии:

- Роль в чипе: «Переработчик» (из `activity_type`, не из `role`).
- Заголовок «Следующий шаг» и пустые состояния без слов «мастерская».
- Блок «Потребности» по умолчанию предлагает способ применения «переработка» (поле потребности, не новый модуль).
- Заявки, получение, подтверждение использования - те же экраны и те же правила, что у BUYER.

Нового модуля для переработчика не создаётся.

### 2.4 ADMIN

В приложении главного экрана нет. Если пользователь `admin` вошёл в клиент ARTA, показывается экран «Вход для администраторов выполняется в панели», со ссылкой на `/admin` и кнопкой «Выйти» (п. 5). Сервер на обычных маршрутах возвращает 403 (`docs/api.md` §5, допущение 15).

## 3. Основные пути пользователя

Нотация: экран → действие → ответ системы. Точка подтверждения помечена [ПОДТВЕРЖДЕНИЕ] и означает явное действие человека (кнопка или диалог); сервер повторно проверяет версию, права и остатки. Ошибки по общей таксономии из п. 6.

### 3.1 SUPPLIER

Путь A: от партии до плана (CLAUDE.md §2 шаги 2-6)

1. Главная → «Создать партию» → форма создания (реализовано).
2. Сохранить черновик → карточка партии (реализовано). Фото добавляются после первого сохранения.
3. Карточка → «Проанализировать фото» → экран анализа ИИ (реализовано): «Предложение ИИ» отдельно от «Ваших значений».
4. [ПОДТВЕРЖДЕНИЕ 1] «Подтвердить характеристики» → «Подтверждено», автор и дата. ИИ никогда не подтверждает.
5. [ПОДТВЕРЖДЕНИЕ 2] «Опубликовать» → диалог (V-7) → статус «Доступно» (реализовано).
6. Подбор покупателей и план (цель, экранов нет): карточка → «Подобрать покупателей» → список с баллом и причинами; «Построить план» → три направления, ожидаемая ценность с меткой «Ожидается», остаток, сравнение с базовым вариантом. План ничего не резервирует.

Путь B: ответ на заявку (шаг 7)

1. Главная или «Сделки» → заявка pending (цель).
2. [ПОДТВЕРЖДЕНИЕ 3] «Подтвердить резерв» (диалог: сколько кг будет удержано). Конфликт остатка → 409 и баннер «Данные изменились, обновите».
3. [ПОДТВЕРЖДЕНИЕ 4] «Отметить передачу» (диалог; повтор безопасен по ключу идемпотентности).
4. Отказ: «Отклонить» с причиной.

Путь C: внутреннее использование (цель)

Карточка → «Использовано внутри предприятия» → ввод кг → [ПОДТВЕРЖДЕНИЕ 5] диалог. Масса не может превысить свободную.

### 3.2 BUYER

Путь A: от потребности до получения

1. «Организация» или блок «Мои потребности» → «Добавить потребность» (типы, состояния, min/max кг, бюджет, город) (цель).
2. «Каталог» → карточка опубликованной партии (реализовано; поля только публичные).
3. «Подать заявку» → ввод кг, цены → [ПОДТВЕРЖДЕНИЕ 1] диалог с итогом («Заявка не списывает деньги и не гарантирует запас до подтверждения продавцом»). Без оплаты.
4. «Заявки» → статус: ожидает → подтверждена → передана.
5. [ПОДТВЕРЖДЕНИЕ 2] «Подтвердить получение» (complete).
6. [ПОДТВЕРЖДЕНИЕ 3] «Подтвердить использование» (отдельный факт, не то же, что получение), с вводом кг, не больше полученного.

Отмена: свою заявку в pending или confirmed можно отменить (диалог).

### 3.3 RECYCLER

Путь тот же, что BUYER A. Отличия: при добавлении потребности по умолчанию выбран способ применения «переработка»; подтверждение использования - «Принято в переработку» (то же действие reuse-confirmation, другая подпись, если владелец одобрит; иначе общая). Отдельных статусов нет.

### 3.4 ADMIN

Вход в `/admin` → сводка (`/admin/api/summary`) → таблицы записей с поиском → [ПОДТВЕРЖДЕНИЕ] «Отключить доступ» / «Включить доступ» пользователя (диалог; учётную запись admin нельзя отключить - сервер вернёт 409 `ADMIN_ACCOUNT_PROTECTED`).

## 4. Переключение организации

Факт: в MVP один пользователь принадлежит одной организации (CLAUDE.md §4; `AuthUser.organizationId` единственное; регистрация всегда создаёт новую организацию и не позволяет присоединиться к существующей, `docs/api.md` §6.1). Переключателя в коде нет, API его не поддерживает.

Поэтому дизайн разделён на два уровня.

Сейчас (реализуемо без изменений API):
- Чип организации в верхней строке главной (`_TopRow`): аватар с инициалами, название организации, подпись «Роль: Предприятие / Покупатель / Переработчик». Это не переключатель, а индикатор. Для переработчика роль берётся из `activity_type`.
- Нажатие по чипу открывает экран «Организация» (сейчас чип не нажимается; ссылка есть в меню и во вкладке) - небольшая правка, цель.
- Выход из аккаунта: «Меню» → «Выйти» (реализовано). Смена организации = выйти и войти другой учётной записью.

Цель, если владелец решит поддержать несколько организаций (решение 2; зависимость от backend-engineer: модель членства, выбор активной организации в токене, права на каждый запрос):
- Расположение: чип организации на главной становится кнопкой; открывает нижний лист «Организации» с выбором (радио-строки по 56 dp, паттерн листа из `visual-system.md` §5.2).
- Что видно при нескольких: в каждой строке название, город, роль в этой организации (чип «Предприятие» / «Покупатель» / «Переработчик»), у активной - значок «выбрано» и текст. Одна организация: лист не открывается, чип без шеврона.
- Роль в чипе всегда показывается текстом, не только цветом. Для разных ролей в разных организациях переключение перестраивает нижнюю навигацию и главный экран целиком; перед этим сброс кэшей провайдеров, чтобы данные одной организации не показывались в другой.
- Подтверждение: переключение не подтверждается диалогом, но выдаёт `snackbar` «Активная организация: {название}» и объявляется скринридеру.
- Права проверяет сервер по активной организации в токене; список организаций с клиента не принимается на веру.

## 5. Общие экраны и зависимость от роли

Не дублировать модули: один экран, роль меняет только данные, подписи и допустимые действия через уже существующие компоненты (`AppTabShell`, `AppButton`, `AppLinkCard`, `MaterialStatusChip`, `AppEmptyState`, `AppErrorState`, `AppSkeleton`). Новые параллельные «buyer_catalog» и «supplier_catalog» не создаются: сейчас каталог один (`CatalogScreen`), подпись вкладки «Партии» или «Каталог» берётся из роли (`tab_shell.dart`).

| Экран | Маршрут | Что общее | Что зависит от роли |
| --- | --- | --- | --- |
| Вход | `/login` | Всё | Ничего до входа. После входа переход на `/` и сборка навигации по роли. Демо-блок «Демо-вход» только в демо-режиме. |
| Регистрация | `/register` | Поля, проверки | Выбор «Предприятие» / «Покупатель»; для покупателя тип «Мастерская» / «Переработчик» (реализовано: `ActivityType.workshop, recycler`). `admin` не предлагается никогда. |
| Подтверждение email | `/verify-email` | Весь экран (шесть ячеек кода, повторная отправка) | Ничего. Реализован; реальная доставка писем не проверена (блокер в `docs/api.md` §23). |
| Профиль / Организация | `/organization` | Форма названия, города, контактов, выход | Строка «Роль» (только чтение); для предприятия и покупателя разные подсказки; блок «Мои потребности» только у покупателя и переработчика (цель); у предприятия - «Мои партии» как ссылка (цель). |
| Каталог | `/materials` | Список, карточка партии, фильтры | Предприятие: свои партии, все статусы, действие «Создать». Покупатель: только опубликованные, поля `MaterialPublicOut`, без создания. |
| Карточка партии | `/materials/:id` | Фото, характеристики, масса | Владелец видит чек-лист публикации, «Изменить», «Архивировать», блок ИИ; покупатель - только публичные поля, «Свободно» и «Подать заявку» (цель). |
| Анализ ИИ | `/materials/:id/analysis` | - | Только владелец-предприятие. |

Выходные подписи роли: `enterprise` → «Предприятие», `buyer` → «Покупатель», `buyer`+`recycler` → «Переработчик». Подпись строится в одной функции в `core/`, а не в каждом экране (сейчас в `home_screen.dart` есть только две подписи, переработчик не различается).

## 6. Что скрыто от роли и почему

Правило: интерфейс скрывает то, что роль всё равно не может сделать, чтобы не показывать мёртвые кнопки. Это не защита. Каждое действие и каждый вложенный ID (фото, анализ, заявка, план) проверяются сервером на роль, организацию и владение; прямой вызов маршрута в обход интерфейса получает 403 или согласованный 404.

| Элемент | SUPPLIER | BUYER / RECYCLER | ADMIN | Причина (серверное правило) |
| --- | --- | --- | --- | --- |
| Создать / изменить / опубликовать / архивировать партию | да (своя) | скрыто | скрыто | `POST/PATCH /materials*` - только владелец, иначе 403 |
| Фото, ИИ-анализ, подтверждение характеристик | да (своя) | скрыто | скрыто | `/ai/*` и confirm - только владелец |
| Построить план, подбор покупателей | да | скрыто | скрыто | `/optimization/*`, `/ai/match` - только `enterprise` |
| Подтвердить / передать / отклонить резерв | да | скрыто | скрыто | `PATCH /reservations/{id}` confirm, transfer - продавец |
| Подать заявку, получить, подтвердить использование | скрыто | да | скрыто | `POST /reservations`, `complete`, reuse-confirmation - покупатель сделки |
| Потребности (создать и править) | скрыто | да (свои) | скрыто | `POST/PATCH /buyer-requirements` - только `buyer` |
| Чужие черновики, планы, аналитика | скрыто | скрыто | скрыто | Принадлежность организации проверяется на каждом запросе |
| Контакты и коммерческие данные чужой организации | скрыто | только участник своей сделки | - | Раскрываются только участникам сделки |
| Любой экран ARTA кроме выхода | скрыто | - | скрыто | Для `admin` на обычных маршрутах по умолчанию 403 |

Дополнительно: подпись роли в чипе и набор вкладок строятся из ответа сервера (`AuthUser.role` и данные организации), не из локального хранилища, которое пользователь может изменить; даже поддельная роль на клиенте не даёт прав. Деньги, остатки и цены на клиенте не вычисляются.

## 7. Админ: отдельный вход, не публичный

Решение дизайна: админ-панель живёт отдельно от приложения ARTA. Backend уже отдаёт `GET /admin` как собственный интерфейс и `/admin/api/*` (`docs/api.md` §22). Во Flutter-клиенте нет ни пункта меню, ни вкладки, ни ссылки на админ-раздел, ни выбора роли «Администратор» при регистрации.

Почему не публичный и не скрытый раздел внутри приложения:
1. `admin` создаётся только серверной консолью; публичной возможности выбрать роль нет и быть не должно (CLAUDE.md §4, §11).
2. Скрытый пункт «по клику на логотип» ничего не защищает и создаёт ложное чувство защиты. Защита - Bearer-токен активного `admin` на каждый запрос.
3. Отдельная поверхность не раздувает мобильный клиент и не требует навигации по ролям внутри Flutter.
4. Админ-токен и токен обычного пользователя не должны смешиваться на одной странице входа.

Минимальный набор экранов админа (уже описан в API, дизайн UI панели принадлежит её автору; здесь только перечень):
1. Вход (email, пароль). Ошибки как на обычном входе; не-админу - «Недостаточно прав.».
2. Сводка: счётчики, зарегистрированная и свободная масса, выручка завершённых сделок (поля `/admin/api/summary`; подписи видов значений те же, что в `dashboard.md`).
3. Записи: таблица с вкладками ресурсов (пользователи, организации, партии, потребности, резервы, сделки, анализы, планы), поиск `q`, пагинация по 20.
4. Управление доступом пользователя: переключатель «Активен» с подтверждающим диалогом; учётная запись admin защищена.

Не входит (CLAUDE.md §2): многоуровневая админ-панель, модерация контента, чат, редактирование записей.

Если администратор вошёл в клиент ARTA: экран-заглушка (п. 2.4), без доступа к вкладкам. Вопрос о том, нужна ли сама эта заглушка, а не просто сообщение при входе, - см. решение 4 в п. 10.

## 8. Состояния

Применяются к каждому экрану; детали и тексты уже в `states.md`, `visual-system.md` §5.7-5.9 и `phase-2-materials.md`. Здесь только то, что относится к навигации.

| Состояние | Как показывать | Навигация |
| --- | --- | --- |
| Загрузка | Скелет окончательной раскладки (показывать через 150 мс, держать не менее 300 мс). Без полноэкранного индикатора. «Загрузка…» один раз для скринридера. | Нижняя панель видна и активна. |
| Пусто | Иконка 64 dp, заголовок, одно предложение, не более одной кнопки. SUPPLIER: «Партий пока нет. Добавьте первую.» и «Создать партию». BUYER: «Пока нет опубликованных партий.» и «Открыть каталог». Фильтр без результата: «Ничего не найдено. Измените фильтры.» и «Сбросить фильтры». | Панель видна. |
| Ошибка (сеть, 5xx) | Панель с текстом из конверта ошибки дословно, «Код обращения: {request_id}» для 5xx, кнопка «Повторить». | Панель видна. |
| 401 | «Сессия истекла. Войдите снова.» и переход на `/login` (охранник маршрута уже перенаправляет при `isAuthenticated = false`). | Панель скрыта. |
| 403 (отказ) | Панель на месте контента: «Нет доступа к этому разделу.», кнопка «На главную». Без «Повторить». Не пытаться угадать причину. Если роль в сессии изменилась - обновить профиль и пересобрать навигацию. | Панель видна, активная вкладка остаётся прежней. |
| 404 (не найдено) | «Объект не найден или недоступен.» и «На главную». Сервер намеренно не различает «нет» и «чужой скрытый»; клиент тоже не различает (не писать «чужая партия»). | Панель скрыта на деталях, видна на вкладках. |
| 409 | Баннер «Данные изменились. Обновите.» с кнопкой «Обновить данные»; остаётся, пока не использован. | Без изменений. |
| 429 | «Слишком много запросов. Повторите через минуту.» | Без изменений. |
| Неизвестный маршрут | Тот же экран, что 404. В `router.dart` не задан `errorBuilder`; цель - добавить. | Панель скрыта. |
| Демо-режим | Баннер «Демо: синтетические данные, не реальные» остаётся на всех экранах и над навигацией. | - |

Фокус после ошибки уходит на заголовок панели ошибки; диалоги возвращают фокус на вызвавший элемент; повторная отправка во время запроса блокируется (`AppButton.loading`), сервер дополнительно защищает идемпотентностью.

## 9. Что уже реализовано и чего нет

Реализовано (по коду):
- Маршруты: `/`, `/login`, `/register`, `/verify-email`, `/materials`, `/materials/new`, `/materials/:id`, `/materials/:id/edit`, `/materials/:id/analysis`, `/organization`. Охранник `authRedirect`: неавторизованный уходит на `/login`, авторизованный со страницы входа - на `/`.
- Нижняя навигация / рейл: `AppTabShell` с тремя вкладками (Главная, «Партии» для предприятия или «Каталог» для остальных, Организация), иконка плюс подпись, переключение через `context.go`.
- Главная: чип организации и роли (две подписи: «Предприятие» и «Покупатель»), «Меню» (организация, выход), приветствие, «Следующий шаг», горизонтальная лента партий, состояния загрузки, ошибки и пусто. Кнопка создания только у предприятия.
- Регистрация с типами деятельности (для покупателя: мастерская и переработчик), без `admin`. Экран подтверждения email.
- `UserRole` в клиенте: `enterprise`, `buyer`, `admin`; неизвестное значение превращается в `buyer`.

Нет:
- Подписи «Переработчик» в чипе роли (определяется по `activity_type`, сейчас показывается «Покупатель»).
- Вкладок для сделок, заявок, потребностей, аналитики; экранов matching, плана, заявок, потребностей, аналитики. Главная не использует `GET /analytics/summary`.
- Определение «Следующий шаг» по заявкам.
- Реакция клиента на роль `admin` (сейчас такой пользователь увидел бы интерфейс покупателя, а сервер ответил бы 403 на запросы каталога).
- `errorBuilder` для неизвестного маршрута; единая панель 403 и 404 на уровне маршрутов (проверить в `states.md` и существующих экранах).
- Переключение организаций: нет ни в клиенте, ни в API.
- Нажимаемый чип организации.
- Вход в `/admin` ссылкой из клиента (и не должен быть).

Зависимости от других ролей: backend-engineer - подтвердить, что `activity_type` возвращается в профиле, чтобы определить переработчика на клиенте; frontend-engineer - расчёт подписи роли в одном месте; qa-engineer - тесты на то, что `admin` не видит вкладок и что скрытые кнопки не заменяют 403.

## 10. Решения для владельца

1. Нужна ли отдельная вкладка «Сделки» у предприятия и «Заявки» у покупателя уже сейчас, до готовности экранов? Рекомендация: нет, добавлять вкладку вместе с экраном (иначе мёртвый пункт), до этого показывать заявки карточкой «Следующий шаг» на главной.
2. Поддерживаем ли несколько организаций у одного пользователя? Рекомендация: нет в MVP (CLAUDE.md §4); чип организации остаётся индикатором, смена - выход и вход. Если да, backend-engineer должен ввести модель членства и активную организацию, а дизайн п. 4 «Цель» применяется.
3. Нужна ли отдельная вкладка «Аналитика» или достаточно блока на «Главной»? Рекомендация: блок на главной, пока нет трёх и более экранов аналитики.
4. Оставляем ли админ-панель только отдельным веб-входом `/admin` (рекомендация) и экран-заглушку для `admin` в клиенте, или заставляем `admin` входить в панель из клиента кнопкой?
5. Переработчик остаётся покупателем с типом `recycler` (рекомендация, как в CLAUDE.md), с другой подписью и подсказками, или получает собственную главную?
6. Подтверждение использования у переработчика называть «Принято в переработку» (рекомендация) или оставить общую подпись?
