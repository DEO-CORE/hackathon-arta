## D-01 — Стек MVP
- **Дата:** 2026-11-06
- **Решение:** Frontend — Flutter + Riverpod. Backend — FastAPI, Pydantic v2, SQLAlchemy 2.x, Alembic, PostgreSQL. Файлы — Supabase Storage (закрытый bucket, подписанные ссылки). Vision AI — внешний провайдер за адаптером.
- **Причина:** совпадает с `CLAUDE.md` §3; минимум новых сущностей для 48 часов.
- **Альтернативы:** Django (тяжелее для 48 часов), микросервисы (запрещены §2).
- **Владелец:** orchestrator

## D-02 — Солвер оптимизации: SciPy `milp`
- **Дата:** 2026-11-06
- **Решение:** один солвер — `scipy.optimize.milp` (MILP с бинарными переменными для минимального заказа и фиксированных расходов).
- **Причина:** одна зависимость с NumPy/SciPy, нет отдельного C++-бинарника; задача мала (десятки партий × десятки потребностей), MILP решается быстро.
- **Альтернативы:** OR-Tools (CP-SAT или MIP). Не используются одновременно (§8). Возврат к OR-Tools — отдельным решением.
- **Владелец:** optimization-engineer

## D-03 — Расположение модулей
- **Дата:** 2026-11-06
- **Решение:**
  - совместимость и matching: `backend/app/optimization/compatibility.py`, `backend/app/optimization/matching.py`;
  - оптимизатор: `backend/app/optimization/allocator.py`;
  - AI-адаптер и задачи анализа: `backend/app/ai/`;
  - vision-провайдер: `backend/app/integrations/vision/`;
  - Storage: `backend/app/integrations/storage/`.
- **Причина:** единый владелец пути на модуль (`DEPENDENCIES.md` §3). `CLAUDE.md` §12 упоминает `services/matching` и `services/optimization`; выбран один модуль, чтобы не дублировать совместимость.
- **Владелец:** orchestrator

## D-04 — Совместимость — одна функция
- **Дата:** 2026-11-06
- **Решение:** одна функция `is_compatible(material, requirement, rules)` и одна версия правил скоринга. Matching и оптимизатор импортируют её; тест проверяет идентичность.
- **Причина:** `CLAUDE.md` §7–8.
- **Владелец:** optimization-engineer

## D-05 — Деньги и масса
- **Дата:** 2026-11-06
- **Решение:** в PostgreSQL — `NUMERIC`; масса `NUMERIC(12,3)` (кг), деньги `NUMERIC(14,2)` (KGS). В Python — `Decimal`. В JSON — строки. `float` не используется.
- **Владелец:** backend-engineer

## D-06 — Авторизация
- **Дата:** 2026-11-06
- **Решение:** пароли — Argon2id (библиотека `argon2-cffi`). JWT (HS256) с allowlist алгоритмов, проверкой `exp`; срок access token — 60 минут (допущение). `JWT_SECRET` обязателен вне тестов, встроенного значения по умолчанию нет. Роль `admin` при регистрации не назначается.
- **Владелец:** backend-engineer

## D-07 — AI-задачи без очереди
- **Дата:** 2026-11-06
- **Решение:** задача анализа сохраняется в БД до запуска; запуск — FastAPI `BackgroundTasks`; при старте приложения задачи в `pending`/`running` переводятся в `interrupted`. Ограничение параллелизма — семафор на процесс.
- **Причина:** `CLAUDE.md` §6 допускает для 48 часов; внешняя очередь не нужна.
- **Ограничение:** не надёжная очередь; при нескольких инстансах потребуется пересмотр.
- **Владелец:** ai-engineer

## D-08 — Транзакции резервов
- **Дата:** 2026-11-06
- **Решение:** подтверждение резерва — `SELECT ... FOR UPDATE` строки партии, затем строки потребности, в фиксированном порядке (сначала `materials`, затем `buyer_requirements`, по UUID). При конфликте — 409.
- **Владелец:** backend-engineer

## D-09 — Время старта хакатона
- **Дата:** 2026-11-06
- **Решение:** `START` не записан (BLK-01 открыт). Таймлайн в `CLAUDE.md` §17 относительный, пока пользователь не укажет время.

## D-11 — Мобильный контракт Фазы 1 (2026-11-07)
- **Решение:**
  - фото загружаются multipart через backend, не presigned (проверки сигнатуры и размеров до сохранения, CLAUDE.md §11); 413/415 не используются, ошибки формата — 422 `UNSUPPORTED_IMAGE`;
  - `AnalysisOut.mode` со значениями `live` / `mock` / `fallback` добавлен в контракт; финальное определение согласует ai-engineer с CON-02;
  - маршруты `POST /materials/{id}/publish` включены в P0 (без них покупатель не видит партию); `archive` — P1, можно убрать из MVP;
  - бюджет покупателя (`budget_per_kg`) не отдаётся enterprise и не попадает в match, план и резерв;
  - резерв создаёт только покупатель; продавец подтверждает резерв. Кнопки «применить план» у продавца нет;
  - сроки BE-01…BE-04 из `api.md` §17.16 — предложение, привязка к START (BLK-01) открыта.
- **Владелец:** orchestrator; контракт — backend-engineer.

## D-12 — Идемпотентность резервов на клиенте и 409 с остатком (2026-11-07)
- **Решение:**
  - клиент создаёт `Idempotency-Key` при нажатии «Забронировать» и переиспользует его для повторов того же запроса; новый ключ — только после изменения данных формы или завершённой попытки;
  - backend обязан возвращать `details.available_kg` в 409 `INSUFFICIENT_STOCK` для `POST /reservations` и для `PATCH /reservations/{id}` (action confirm);
  - `PRECONDITION_FAILED` используется с разными `details`; клиент должен различать причины по полю `details.reason`, которое backend обязан добавить (BE-06).
- **Владелец:** orchestrator (решение); backend-engineer (реализация); flutter-developer (клиент); qa-engineer (MI-08…MI-10).
