# ARTA - план тестирования по ролям (QA)

Статус: ПЛАН. Ни один кейс не запускался; PASS ставится только после фактического прогона с записанным выводом. Дата: 2026-11-07. Владелец: QA.
Источники: `CLAUDE.md` §4, §5, §9, §11; `docs/api.md` разделы 1-23 (особенно 1.1, 1.2, 5, 12, 15, 20-23); `docs/qa/authorization-matrix.md` (NID-01..20, FLD-01..05), `test-plan.md`, `lifecycle-test-plan.md`, `race-cases.md` (RC-nn), `invariants.md` (INV-nn), `email-verification-plan.md` (EV-nn). Каталога `docs/architecture/` в репозитории нет; документ строится по api.md и CLAUDE.md §4. Кейсы из перечисленных документов здесь не дублируются, а адресуются по ID.

## 0. Допущения и условные обозначения

- Роли API: `enterprise`, `buyer`, `admin` (только консоль, `app.create_admin`). Переработчик = `buyer` + `organization.activity_type = recycler`; отдельных прав у него нет (api.md 1.1, A-5). "Подтверждение переработки" в этом плане = `POST /transactions/{id}/reuse-confirmation` (подтверждение фактического использования переданной массы).
- Один пользователь - одна организация. Членства, приглашений, смены роли и смены организации в API v1 нет (grep по `docs/` не нашёл ни одного описания). Строки таблиц про приглашения и смену роли описывают ожидаемое "отсутствие функции" (404/405, без побочных эффектов) и помечены БЛК/РЕШ, пока владелец не решит иначе (раздел 6).
- 403 = известное, но запрещённое по роли действие; 404 = объект отсутствует или скрыт от этого пользователя (api.md 1.1). Для неизвестного маршрута 404 `NOT_FOUND`, для неверного метода 405 (A20-5).
- Admin на публичных маршрутах: по умолчанию 403 (api.md 16, п.15). Исключение: `/admin` и `/admin/api/*` (раздел 22).
- Порядок проверок (A20-6, 23.4): 401 -> 403 роль -> 429 -> 422 тело (до 404 по владению, отклонение от 19.1) -> 404 владение -> 409 состояние. Тесты не должны ожидать "404 раньше 422" для кривого тела.
- Метки: U unit, I integration (PostgreSQL), RC гонки, A API (живое приложение), W widget, D устройство через adb. Метки в колонках: БЛК - сейчас нельзя проверить (раздел 5); РЕШ - ожидание зависит от решения владельца (раздел 6).
- Роли в коде кейсов: E1/E2 (enterprise разных организаций), B1/B2 (buyer), R1 (buyer-recycler), AD (admin), ANON.

Аудит (SEC-29). Журнала аудита в api.md нет, кроме неявных следов: `confirmed_at/by`, автор подтверждения impact_record, `cancel_reason`, события "подтверждено демо-кодом" (23.5), `request_id` в логах. Кейсы выставляются как "фиксируем фактическое" и не считаются пройденными, пока владелец не определит состав аудита (раздел 6, п.5):
- AUD-1: каждое состояние-меняющее действие (confirm/cancel/transfer/complete/internal-use/reuse-confirmation/publish/archive/admin access) оставляет след с user_id, organization_id, действием, объектом, временем UTC, request_id; запись создаётся в той же транзакции и откатывается вместе с ней.
- AUD-2: неуспешные попытки (403/404 на чужом объекте, неверный код email, login-brute-force) логируются безопасным кодом без пароля, токена, кода, подписанных URL.
- AUD-3: журнал не доступен обычным ролям; admin видит его только через `/admin/api/*`, без секретов.

## 6. Решения для владельца, влияющие на ожидания тестов

1. Приглашения и членство: остаётся ли "один пользователь - одна организация без приглашений" на весь MVP? Ожидание теста: любые маршруты приглашений дают 404/405. Если приглашения нужны, нужен контракт (роли приглашённого, срок, одноразовость) до написания SEC-16.
2. Смена роли/деактивация при живом токене: проверять ли роль и `active` из БД на каждом запросе (тогда 401/403 со следующего запроса) или доверять claim до exp (60 мин)? Для деактивации план ожидает немедленный 401; для смены роли ожидание не зафиксировано.
3. Политика 403 против 404: подтвердить правило "роль не подходит -> 403 даже для чужих ID; роль подходит, объект чужой -> 404" как единое для всех маршрутов, включая `/admin/api/*`. Иначе M-матрица перестраивается.
4. Права admin: остаётся ли admin вне публичного API (403 на всех обычных маршрутах) и ограничивается ли только `/admin/api/*`; нужна ли модерация партий.
5. Аудит: нужен ли журнал действий в MVP, какие события и срок хранения; без решения AUD-1..3 не засчитываются.
6. Фазы R0-R7: подтвердить нарезку из раздела 4 или передать официальную; а также считать ли `reuse-confirmation` "подтверждением переработки" (в плане - да, роль buyer с activity_type recycler, отдельной роли нет).
