# ARTA — инварианты (QA-01 / QA-05)

Статус: план; ни одна проверка не запускалась. Источник: `CLAUDE.md` §5, §8, §10, `docs/decisions.md` D-05.
Принцип: инварианты проверяются запросом к БД и ответам API после каждой операции в e2e/race-тестах, а не только в unit-тестах расчёта. Проверочный SQL/хелпер — в `backend/tests/` (QA-владение: `e2e/`, `race/`).

## 1. Баланс массы

Обозначения: T = `total_kg`, A = available, H = held (активные confirmed-резервы), X = transferred, U = internally_used.

| ID | Инвариант | Когда проверять | Как |
|---|---|---|---|
| INV-01 | T = A + H + X + U | после каждой операции: создание, publish, confirm, cancel, transfer, complete, internal-use, архивация | SQL по партии, точное равенство Decimal |
| INV-02 | A ≥ 0, H ≥ 0, X ≥ 0, U ≥ 0 | то же, и после каждого race-кейса | SQL CHECK и тест |
| INV-03 | T > 0 для published партии; T не уменьшается при продаже | после transfer и complete | сравнение T до/после |
| INV-04 | Каждая масса учтена один раз: передача переносит H в X (H уменьшается ровно на X-прирост) | transfer | дельты H и X равны, A не меняется |
| INV-05 | confirm: A уменьшается, H растёт на то же значение; cancel confirmed — обратно | confirm/cancel | дельты |
| INV-06 | pending-заявка не меняет A и H | create reservation | сравнение до/после |
| INV-07 | internal-use: A уменьшается, U растёт на то же значение; создан ровно один impact_record | internal-use | дельты + count |
| INV-08 | Статус партии вычисляется единым правилом: `available` (A=T), `partially_allocated` (A>0 и H+X+U>0), `reserved` (A=0, H>0), `completed` (X+U=T, H=0), `archived` (скрыта, H=0) | после каждой операции | таблица ожидаемых статусов по состояниям (параметризованный тест) |
| INV-09 | Точность: масса кратна 0.001, деньги кратны 0.01; JSON-значения строки; в ответах нет `float`/научной нотации | выборочно по всем ответам DTO | схема + регэксп |
| INV-10 | Предложенный план не изменяет T, A, H, X, U и статус партии | `POST /optimization/run` | сравнение снимков до/после |
| INV-11 | Сумма удержаний по потребности ≤ её `remaining_demand_kg` (исходный спрос); `remaining_demand_kg ≥ 0` | confirm/cancel | SQL |

## 2. Подтверждённое использование

| ID | Инвариант | Как проверять |
|---|---|---|
| INV-20 | Сумма подтверждений использования по транзакции ≤ фактически переданные кг этой транзакции | попытка превысить → 409/422; SQL-сумма |
| INV-21 | Сумма подтверждённого использования по организации ≤ (переданное покупателю + его внутреннее использование) | SQL по всем impact_records |
| INV-22 | Подтверждение использования возможно только после transferred; на pending/confirmed/cancelled — отказ | параметризованный по статусам |
| INV-23 | reuse-confirmation не меняет X, A, H, revenue; создаёт ровно один impact_record типа «подтверждённое использование» | дельты |
| INV-24 | Повтор reuse-confirmation (тот же ключ) не увеличивает сумму; разные ключи суммируются, но с учётом INV-20 | RC-34, RC-35 |
| INV-25 | Внутреннее использование (impact_record) и подтверждение покупателя учитываются как разные типы фактов и не складываются дважды в «confirmed reuse» одной и той же массы | сценарий: internal-use 10 кг + transfer 10 кг + reuse 10 кг → confirmed reuse по аналитике = 10 (покупатель) или по определению api.md, без дублирования |
| INV-26 | impact_record содержит автора, дату подтверждения и основание | проверка полей |
| INV-27 | У одной transaction один reservation (UNIQUE), число transactions ≤ число reservations в статусах transferred/completed | SQL |

## 3. Выручка и прогноз

| ID | Инвариант | Как проверять |
|---|---|---|
| INV-30 | Revenue = сумма `sale_amount` по completed-сделкам; transfer, reserve, внутренняя экономия, прогноз плана не увеличивают её | сценарии: reserve → revenue 0; transfer → 0; complete → сумма |
| INV-31 | Создание/пересчёт плана оптимизации не меняет `revenue`, `distributed_kg`, `confirmed_reuse_kg` | сравнение `/analytics/summary` до/после `optimization/run` |
| INV-32 | Прогнозные поля (`forecast_*`) передаются отдельно от фактических и помечены; фактические поля не содержат прогноз | проверка структуры ответа |
| INV-33 | Registered kg = сумма T по опубликованным/существующим (не archived/draft по api.md) партиям, без повторного суммирования событий | добавление событий не меняет registered |
| INV-34 | Distributed kg = H + X (активный резерв + переданное), без двойного счёта; cancelled не входит; transferred не считается дважды (H→X) | reserve → transfer: значение не растёт |
| INV-35 | Available/unallocated = сумма A; прогнозный остаток плана — отдельное поле | сравнение |
| INV-36 | Allocation efficiency = distributed / registered × 100; при registered=0 → 0 | пустой датасет, 1 партия, дробные значения, округление |
| INV-37 | Пустой датасет: все поля 0/пустые, без 500 и деления на ноль | свежая БД |
| INV-38 | Revenue организации не включает чужие сделки | две пары организаций |
| INV-39 | Прогноз использует ту же сумму сделки, что и фактическая выручка, только после complete (отсутствие «подмены») | нет роста revenue при росте прогнозных полей |
| INV-40 | CO2 в аналитике не вычисляется (поле отсутствует/null) | проверка схемы ответа |
| INV-41 | Различие передано/использовано: рост X не меняет confirmed_reuse | дельты |

## 4. Оптимизация и matching

Привязаны к синтетическому fixture (`BE-09`); эталоны считаются вручную и пишутся в тест заранее, а не из вывода кода.

| ID | Инвариант | Как проверять |
|---|---|---|
| INV-50 | Для каждой партии сумма x по направлениям ≤ A; остаток = A − сумма, явно возвращён | проверка плана |
| INV-51 | Для каждой потребности сумма x по всем партиям ≤ `remaining_demand_kg` | то же, общий спрос между партиями |
| INV-52 | x = 0 для пар, не прошедших `is_compatible` (одна функция с matching) | тест, что matching и оптимизатор импортируют один объект |
| INV-53 | min-lot: для каждой пары либо x = 0, либо min_kg ≤ x ≤ upper | параметризованный |
| INV-54 | Отрицательная чистая ценность на кг не получает массу (если нет обязательности) | малый набор |
| INV-55 | Малый набор с заранее известным оптимумом: objective совпадает с ручным расчётом | эталон |
| INV-56 | Повторяемость: два прогона на одном snapshot дают идентичный план | сравнение JSON |
| INV-57 | Baseline допустим на тех же входах (INV-50..53) и objective_opt ≥ objective_baseline на fixture | сравнение |
| INV-58 | Статус `feasible`/`heuristic`/`timeout` не отображается как `optimal` | API и UI-подпись |
| INV-59 | После округления до 0.001 кг баланс, спрос, совместимость сохраняются | edge-кейс из OPT-03 |
| INV-60 | Отсутствующая цена не трактуется как 0: вариант исключён с объяснением | тест |
| INV-61 | Нулевой остаток и нулевой спрос → пустой план без ошибки | тест |
| INV-62 | Matching: hard-фильтры первичны; неизвестные критичные характеристики не дают совпадения; при равном score порядок по requirement_id | тесты |

## 5. Безопасность данных как инвариант

| ID | Инвариант | Как проверять |
