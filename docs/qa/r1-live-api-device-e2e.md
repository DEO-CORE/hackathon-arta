### Нестабильность PostgreSQL-тестов: причина и исправление

Воспроизведено до исправления: два pytest-процесса на одной БД дали 9–10 failed и 33–131 errors. Причины:

1. **Общая БД.** Два процесса одновременно делают `TRUNCATE` и `downgrade/upgrade` одной базы. Это основная причина; прошлый одиночный сбой (6 failed + 4 errors) совпадает с параллельным запуском, но в этой сессии напрямую не воспроизводился без параллели.
2. **`audit_log` не очищался** (нет FK к очищаемым таблицам). Запросы «первая запись `user.access_changed`» читали записи прошлых тестов и прогонов.
3. **Двойная регистрация фикстуры.** `tests/security/conftest.py` реэкспортирует `_migrated_db`, поэтому pytest создаёт её дважды. Наивная блокировка в этом месте вешала один процесс. Держатель блокировки сделан процесс-локальным.

Исправление: в `tests/integration/conftest.py` сессионная `pg_advisory_lock` на `TEST_DATABASE_URL` (второй запуск ждёт, а не ломает первый; при падении процесса сервер снимает блокировку); `TRUNCATE` включает `audit_log`.

Воспроизводимый прогон (из `backend/`, в venv):

```sh
TEST_DATABASE_URL='postgresql+psycopg://arta@127.0.0.1:54329/arta_be_test' python -m pytest -q
```

Ограничение: блокировка защищает только от запусков с этим кодом на одной БД. Отдельные тестовые БД на каждый запуск не создаются.
