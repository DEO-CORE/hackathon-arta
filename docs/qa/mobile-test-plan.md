# ARTA — тест-план мобильного клиента (Flutter), P0-путь

Статус: ПЛАН. Все кейсы имеют статус «план». Ни один кейс не запускался; код `frontend/` на момент составления не принят в проверку, `docs/api.md` — черновик CON-01 (коды ошибок в `docs/design/states.md` помечены `[PROVISIONAL]`). Результаты прогонов будут вноситься отдельно, с сохранённым выводом команд.

Связанные документы: `test-plan.md`, `authorization-matrix.md`, `race-cases.md`, `docs/api.md`, `docs/design/states.md`, `CLAUDE.md` §13, §15, §16.
Тестовый код в `frontend/test/` и `frontend/integration_test/` пишется после Фазы 1; этот документ его не содержит.

Обозначения статуса: «план» — не запущено; «не проверено, блокер» — невозможно без внешнего ресурса.

## 1. Цель

Подтвердить со стороны мобильного клиента P0-путь MVP (`CLAUDE.md` §2):

регистрация/вход → организация → партия → фото → AI-анализ → подтверждение человеком → matching → оптимизация → резерв.

Клиент должен: (а) честно отображать то, что решил сервер; (б) не считать цены, остатки и статусы; (в) не подтверждать AI-результат автоматически; (г) не создавать второй резерв при повторе; (д) показывать безопасные ошибки из конверта и актуальный остаток при 409; (е) явно отделять прогноз от факта и режим Demo от живых данных.

Вне цели: передача/получение/подтверждение использования и аналитика (следующая фаза плана), онлайн-оплата, CO2, кыргызский язык, нативные сборки.

## 2. Уровни проверки

| Уровень | Что проверяет | Среда | Расположение (после Фазы 1) | Метка источника данных |
|---|---|---|---|---|
| Widget | формы, валидация, состояния loading/empty/error/success, тексты ошибок, блокировка кнопок, guard-логика роутера; репозитории подменены fake-объектами | `flutter test` | `frontend/test/` (владелец flutter-developer; QA рецензирует и добавляет недостающие кейсы test-only) | `FAKE` |
| Integration (live) | сценарий Flutter → FastAPI → PostgreSQL на свежей мигрированной БД, mock AI | `flutter test integration_test`, если платформа настроена; запущенный backend | `frontend/integration_test/` (QA) | `LIVE-API` |
| Integration (demo) | тот же сценарий на Demo-репозитории без сети; проверяет UI, не backend | `flutter test integration_test` | `frontend/integration_test/` (QA) | `DEMO-REPO`; результат не засчитывается как проверка API |
| Ручной прогон | телефон (реальное устройство или эмулятор) и ноутбук (Chrome, узкое/широкое окно) | `docs/demo.md`, журнал в `docs/qa/` | — | `LIVE-API` или `DEMO` с пометкой |

Правило: прогон на Demo-репозитории всегда помечается `DEMO-REPO` и не закрывает кейсы, требующие реального API (коды 401/403/404/409/422 от сервера, идемпотентность, права). Прогон с mock AI помечается `mock AI` и не подтверждает работу реального провайдера.

## 6. Правила окружения

| Тема | Правило |
|---|---|
| API_BASE_URL | Задаётся только через `--dart-define=API_BASE_URL=...` и читается через `String.fromEnvironment`; значение по умолчанию не должно указывать на боевой адрес; кейс: сборка без параметра показывает явную ошибку конфигурации или документированный локальный адрес, не молчаливый Demo |
| Запуск live | `flutter run -d chrome --dart-define=API_BASE_URL=http://127.0.0.1:8000` (команда из `CLAUDE.md` §13; выполняется только после появления Flutter-проекта и запущенного backend) |
| Demo | Включается явным флагом/выбором; данные Demo-репозитория лежат отдельно от live-кода и тестовых fixtures; метка «Демо» постоянна; в отчётах прогон Demo помечен `DEMO-REPO` |
| Данные | Только синтетические: вымышленные организации, email в зарезервированных доменах (`example.com`), фиксированные UUID/seed, без реальных контактов и фото реальных предприятий; fixtures подписаны «синтетические данные» |
| Backend для integration | Свежая мигрированная отдельная PostgreSQL `*_test`; mock AI с явной меткой; SQLite не используется; destructive-операции только в тестовой БД |
| Секреты | `.env`, ключи, токены не коммитятся и не печатаются в логах тестов |
| Время и локаль | UTC на сервере; клиент форматирует локально; тесты форматов («12,500 кг», «1 250,00 KGS») фиксируют локаль |
| Устройства | Минимум: узкий экран телефона (портрет), широкий ноутбук (Chrome); ориентация и масштаб шрифта — выборочно |

## 10. Главные риски для демо

1. Несогласованность 409 и идемпотентности на клиенте: если `details.available_kg` не приходит или ключ идемпотентности создаётся неверно (на каждое нажатие), возможны дубль заявки либо неверный остаток у проигравшего покупателя. Проверяется MI-08..MI-10, MP-61..MP-65.
2. Зависимость демо от внешних ресурсов (BLK-02 live AI, BLK-03 Supabase): без них реальный upload и AI не подтверждены; риск подмены в Demo-режиме, воспринимаемой как живая работа. Нужен честно названный режим и кейсы MA-23..MA-25, MB-01..MB-06.
3. Расхождение контракта и клиента при черновом `api.md`: вложенный конверт `{"error": {...}}`, `PRECONDITION_FAILED` для разных причин, предварительные DTO AI/matching/optimization, отсутствие токена при регистрации; один неверный парсер ломает весь P0-путь. Нужна сверка MG-06 после утверждения CON-01..CON-03.
