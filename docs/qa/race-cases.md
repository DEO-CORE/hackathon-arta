# ARTA — сценарии конкуренции и идемпотентности (QA-01 / QA-03)

Статус: план. Ничего не запускалось. Тесты: `backend/tests/race/` на отдельном PostgreSQL (не SQLite). Источник правил: `CLAUDE.md` §5, `docs/decisions.md` D-08.

## 1. Общая схема теста

| Элемент | Правило |
|---|---|
| БД | отдельная тестовая PostgreSQL, свежие миграции, чистка между тестами только в тестовой БД |
| Сессии | две и более независимых HTTP-сессии (разные токены/соединения), старт через барьер (`asyncio.Barrier`/threads), не последовательные вызовы |
| Повторяемость | каждый конкурентный кейс запускать N=20 раз (разный порядок прихода); допускается любой победитель, но исход по классам фиксирован |
| Проверка после | запрос SQL: `available_kg >= 0`, `held_kg >= 0`, баланс `total = available + held + transferred + internally_used`, число строк `transactions`/`impact_records` |
| Коды | победитель 2xx, проигравший 409 (не 500, не deadlock-ошибка наружу) |

## 2. Конкуренция за запас и спрос

Базовая партия M: total 100.000 кг, available 100.000, published. Заявки pending не удерживают запас; удержание возникает при confirm.

| ID | Сценарий | Начальные условия | Ожидаемый результат | Что проверять в БД |
|---|---|---|---|---|
| RC-01 | Два продавца-сессии одновременно confirm двух pending по 60 кг на партию 100 кг (одна сессия владельца с двух клиентов) | M available 100; RES-1 60, RES-2 60 pending | ровно один confirmed, другой 409 | held=60, available=40; нет отрицательных |
| RC-02 | Два confirm на заявки 60 + 40 кг | available 100 | оба успешны, 200 | held=100, available=0, статус партии `reserved` |
| RC-03 | Три confirm по 40 кг | available 100 | ровно два успешны, один 409 | held=80, available=20 |
| RC-04 | Две одновременные `POST /reservations` с разными Idempotency-Key на 70 кг каждая (pending) | available 100 | обе 201 (pending запас не держит) | 2 reservation pending, held=0 |
| RC-05 | Одновременный confirm двух заявок разных покупателей на одну потребность с `remaining_demand_kg` меньше суммы | demand 50; RES-A 30, RES-B 30 на разных партиях | ровно один confirmed, другой 409 (спрос) | `remaining_demand_kg >= 0`, сумма held по потребности ≤ 50 |
| RC-06 | Две партии, два confirm одной потребности в разном порядке (A→B и B→A) | demand ограничен | нет deadlock (500/40P01 наружу), исход 200/409 | блокировки в порядке D-08; логов deadlock нет |
| RC-07 | Confirm конкурирует с `internal-use` владельца на тот же остаток | available 100; confirm 70, internal-use 70 | один успех, другой 409 | `available+held+transferred+internally_used = total`, ≥ 0 |
| RC-08 | Confirm конкурирует с PATCH партии, уменьшающим `total_kg` | active confirm в полёте | PATCH 409 при активных обязательствах; либо confirm 409 по версии | total не стал меньше held+transferred+used |
| RC-09 | Confirm конкурирует с архивацией партии | pending confirm vs archive | один успех, другой 409; archived не имеет активных резервов | нет confirmed-резерва у archived партии |
| RC-10 | Confirm конкурирует с отменой той же заявки (cancel от покупателя) | pending | конечное состояние одно из {confirmed, cancelled}, не оба; удержание согласовано | held = 0 при cancelled, = kg при confirmed |
| RC-11 | Нагрузка: 20 параллельных confirm по 10 кг на партию 100 кг, заявок 20 | available 100 | ровно 10 успешных, 10 × 409 | held=100, available=0, нет отрицательных |
| RC-12 | Мелкая дробность: confirm 0.001 кг × 1000 параллельно на 0.500 кг | available 0.500 | ровно 500 успешных | точное Decimal, без дрейфа |

## 3. Идемпотентность создания и действий

Повтор «того же действия» = тот же ключ идемпотентности или тот же целевой переход на том же объекте.

| ID | Сценарий | Ожидаемый результат | Что проверять |
|---|---|---|---|
| RC-20 | `POST /reservations` повтор с тем же Idempotency-Key и тем же payload (последовательно) | тот же ответ/ID, 200 или 201 по api.md | одна строка reservations |
| RC-21 | То же, но два запроса одновременно (барьер) | оба получают один и тот же reservation_id; нет 500 | одна строка, нет нарушения UNIQUE, наружу не вытекающего |
| RC-22 | Тот же ключ, иной payload (quantity_kg отличается) | 409 | вторая заявка не создана |
| RC-23 | Тот же ключ у другого пользователя | считается другим ключом (область пользователя+операции) | две независимые заявки |
| RC-24 | Тот же ключ для другой операции (область «операция») | независимый | нет ложного совпадения |
| RC-25 | Повтор confirm на confirmed заявку | 200 с прежним состоянием (или 409 по api.md, но единообразно) | held не удвоен |
| RC-26 | Два одновременных confirm одной заявки | оба одинаковый исход, held увеличен один раз | held = kg, не 2×kg |
| RC-27 | Повтор cancel на cancelled | без ошибки/единообразный ответ | held не уменьшен второй раз (не ушёл в минус) |
| RC-28 | Два одновременных cancel confirmed заявки | held возвращён один раз | held = 0, available = исходный |
| RC-29 | Повтор transfer на transferred | один результат | `transactions` ровно одна (UNIQUE reservation_id), transferred_kg не удвоен |
| RC-30 | Два одновременных transfer | одна transaction | то же, нет 500 из-за UNIQUE |
| RC-31 | Повтор complete на completed | без изменений | нет второго impact_record, revenue не удвоена |
| RC-32 | Два одновременных complete | один исход | то же |
| RC-33 | Повтор `internal-use` с тем же ключом | один impact_record, internally_used не удвоен | баланс сохранён |
| RC-34 | Повтор `reuse-confirmation` с тем же ключом/количеством | один impact_record | сумма подтверждений не растёт |
| RC-35 | Одновременные `reuse-confirmation`, суммарно больше переданного | сумма ≤ переданного; лишний 409 | подтверждено ≤ передано |
| RC-36 | Повтор переданного ключа после перезапуска приложения (новый процесс) | тот же исход | ключ хранится в БД, а не в памяти |

## 5. Отмена возвращает удержание

| ID | Сценарий | Ожидание |
|---|---|---|
| RC-50 | confirm 40 из 100, затем cancel | held 0, available 100, статус партии `available` |
| RC-51 | confirm 60 + 40, cancel первой | held 40, available 60, статус `partially_allocated` |
| RC-52 | confirm 100, cancel | `reserved` → `available`, available 100 |
| RC-53 | cancel pending (удержания не было) | held не изменён, не ушёл в минус |
| RC-54 | cancel после чужого cancel конкурирующей заявки | остатки согласованы |
| RC-55 | cancel возвращает спрос потребности (`remaining_demand_kg` восстановлен до исходного) | точно исходное значение |
| RC-56 | после cancel освободившийся запас можно подтвердить другой заявкой (последовательно и конкурентно) | успех, баланс сохранён |
| RC-57 | отказ продавца с причиной (cancel от E) | причина сохранена, held возвращён, покупатель видит cancelled |
