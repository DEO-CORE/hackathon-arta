## 1. Роли (в коде — три, переработчик — подтип)

- **SUPPLIER** = `enterprise`.
- **BUYER** = `buyer`.
- **RECYCLER** = `buyer` с `activity_type=recycler`. Отдельной роли нет. Самозаявление — решение владельца (R-decision-4).
- **ADMIN** = `admin`, только через консоль `create_admin`, только `/admin/api/*`.

## 2. Фазы

Фазы R0–R7 определены этим документом (в репозитории их раньше не было). Оценки — грубые, в рабочих днях одного человека.

### R0 — Выравнивание и решения (1–2 дня, P0)
- **Цель:** синхронизировать документацию с кодом и закрыть решения владельца, блокирующие R1.
- **Зависимости:** нет.
- **Backend:** обновить `docs/api.md` §1.1, §5, §20, §21–23 под фактический код; `TASK_BOARD` — отметить реализованное. (backend-engineer)
- **Flutter:** зафиксировать карту экранов по ролям; подтвердить, что `authRedirect` не меняется. (flutter-developer)
- **UX:** карта навигации по ролям утверждена (`role-based-navigation.md`). (ux-designer)
- **QA:** выбрать из `role-based-test-plan.md` обязательный минимум (раздел 5). (qa-engineer)
- **Критерий готовности:** решения владельца R-decision-1…8 записаны в `docs/decisions.md`; документация согласована с кодом.
- **Риск:** откладывание решений блокирует всё. Параллельно: R2 и R3 не ждут R1.

### R1 — Фундамент: membership и права (6–8 дней, P0 для демо = 0, P1 для продукта)
- **Цель:** заменить `users.role` + `require_roles` на членство и проверку права на каждом запросе.
- **Зависимости:** R0 (решения 1, 2, 8).
- **Backend:** таблицы `organization_memberships`, `audit_log`, поле `organizations.side`, `users.default_organization_id`; функция `require_permission`; миграция с backfill OWNER для текущих пользователей (отдельный шаг, с проверкой «ни один пользователь не потерял доступ»). (backend-engineer)
- **Flutter:** `orgContextProvider`, безопасный default, `authRedirect` с необязательными параметрами роли (по `flutter-role-architecture.md`). (flutter-developer)
- **Миграция:** пошаговая, с режимом зеркала `users.role` на переходе. Организация без однозначной стороны — миграция останавливается, не угадывается.
- **QA:** SEC-01…SEC-12 (межорганизационный доступ, 403/404), интеграционные тесты на PostgreSQL. (qa-engineer, backend-engineer)
- **Критерий готовности:** все существующие тесты зелёные; новые права покрыты тестами; p95 замерен с дополнительным SELECT на запрос.
- **Риск:** ломает существующие тесты (`router_guard_test`, `tab_navigation_test`, `material_navigation_test`, `home_dashboard_test`, `login_screen_test`, `verify_email_test`). Митигация: сначала тестовый хелпер ролей и безопасный default, потом правки.

### R2 — Продавец: вторая половина сделки в UI (5–6 дней, P0 для демо)
- **Цель:** продавец видит подбор с причинами, план с остатком, заявки и подтверждает передачу.
- **Зависимости:** R0. Не требует R1 для демо-версии (демо-роли без членств).
- **Backend:** убрать `min_kg` из публичной схемы потребности чужой организации (решение R-decision-2); `details.reason` для `PRECONDITION_FAILED` в резервах. (backend-engineer)
- **Flutter:** экраны «Подбор» (`/ai/match`, причины), «План» (`/optimization/run`, baseline, остаток, `validate_plan`), «Заявки продавца» (confirm, cancel, transfer), вкладка «Сделки». (flutter-developer)
- **UX:** экраны по `role-based-navigation.md`; без «мёртвых» вкладок — вкладка появляется вместе с экраном. (ux-designer)
- **Критерий готовности:** сценарий «подбор → план → заявка → подтверждение → передача» проходит на телефоне в демо и на живом API.
- **Риск:** план не гарантирует запас; перед резервом всегда повторная проверка (сделано на backend).

### R3 — Покупатель: потребность, подбор, заявка, получение (5–7 дней, P0 для демо)
- **Цель:** покупатель создаёт потребность, видит подходящие партии с причинами, подаёт заявку и подтверждает получение.
- **Зависимости:** R0; для демо — без R1.
- **Backend:** маршрут подбора для покупателя (`POST /buyer-requirements/{id}/matches`, решение R-decision-1, P1); отмена только `pending` покупателем (R-decision-5). (backend-engineer)
- **Flutter:** экраны «Мои потребности», «Заявки» (статусы), «Получение» (`complete`), «Каталог» (уже есть). Минимум по решению R-decision-1 (`role-model.md`): каталог + потребность + заявка + подтверждение получения. (flutter-developer)
- **UX:** «Ждут действия» на главной (счётчик из списков заявок, без push). (ux-designer)
- **Критерий готовности:** покупатель проходит полный цикл заявки на телефоне в демо; повтор нажатия не создаёт вторую заявку.
- **Риск:** переработчик с пустым `uses` блокируется `UNKNOWN_APPLICATION`. Решение R-decision-2: потребность с пустым списком применений для демо.

### R4 — Переработчик и подтверждение использования (2–3 дня, P1)
- **Цель:** переработчик регистрируется как покупатель с `activity_type=recycler`, получает потребность и подтверждает переработку.
- **Зависимости:** R3.
- **Backend:** подтверждение использования (`reuse-confirmation`) — проверка суммы не выше переданного; признак переработчика по организации, а не по `user.role`. (backend-engineer)
- **Flutter:** подпись роли «Переработчик», подтверждение использования на карточке заявки. (flutter-developer)
- **QA:** сценарии подтверждения переработки; отдельно — не превышать переданный объём.
- **Критерий готовности:** подтверждённая переработка видна в аналитике отдельно от прогноза и от передачи.

### R5 — Аналитика и админ-просмотр (2–3 дня, P1)
- **Цель:** аналитика с разделением «прогноз / передано / подтверждённое использование»; админ — только метаданные и блокировка.
- **Зависимости:** R2, R3, R4.
- **Backend:** поля аналитики для покупателя (решение владельца); админ не получает содержимое партий и AI-payload. (backend-engineer)
- **Flutter:** блок аналитики на главной (без нулевых метрик), экран аналитики — после появления данных. (flutter-developer)
- **Админ:** в мобильном клиенте нет; веб `/admin` — как есть.
- **Критерий готовности:** на главной нет нулевых или выдуманных метрик; forecast не увеличивает выручку.

### R6 — ИИ, подбор и оптимизация: режимы и подтверждение (2–3 дня, P0 для демо)
- **Цель:** ИИ показан честно: mock или live на каждом экране; подтверждение человеком; подбор и план подписаны как детерминированные.
- **Зависимости:** R2, R3.
- **Backend:** режим `mode` в ответе; подтверждение через `analysis_id` (сейчас возвращает 409 до AI-02). (ai-engineer, backend-engineer)
- **Flutter:** плашка «Симуляция» / «ИИ-результат, требует проверки»; предложения ИИ отдельно от подтверждённых полей; ни одного слова «Подтверждено» на AI-блоке до нажатия человека. (flutter-developer)
- **Решение владельца:** видит ли покупатель предложения ИИ (вариант A — нет, по умолчанию).
- **Критерий готовности:** AI-SIM-01…07 и AI-API-01 пройдены; mock никогда не подписан как live.
- **Блокер:** BLK-02 (провайдер и ключ). Без него live-часть — «не проверено».

### R7 — Сквозное тестирование, безопасность, демо (3–4 дня, P0)
- **Цель:** один сквозной прогон Flutter → FastAPI → PostgreSQL без `USE_DEMO_DATA`, с записанным результатом; безопасность по SEC-01…33.
- **Зависимости:** R1–R3, R6.
- **QA:** `docs/qa/role-based-test-plan.md` (156 кейсов), прогон на телефоне (12 кейсов adb). (qa-engineer)
- **Backend:** гонки резервирования (отдельная PostgreSQL, две сессии). (backend-engineer)
- **Презентация:** `docs/demo.md`, `claims-check.md` (по `hackathon-role-scope.md`), репетиция Q&A. (orchestrator, jury-simulator)
- **Критерий готовности:** записанный вывод E2E; каждый незапущенный кейс помечен как «не проверено», а не «пройдено».

## 3. Критический путь

R0 → R1 (для продукта) или сразу R2/R3 (для демо) → R2 + R3 параллельно → R6 → R7.

Для демо критичны R2, R3, R6, R7. R1 и R4/R5 — после демо, если решение R-decision-8 позволяет.

## 4. Параллельность

- R2 (продавец) и R3 (покупатель) — разные файлы во Flutter, но общие репозитории: интерфейсы сначала, потом реализации.
- Backend по R2 и R3 — разные таблицы, но общая схема заявок: одна миграция на фазу.
- Не делать параллельно две миграции, трогающие `organizations` или `users`.

## 5. MVP для хакатона (рекомендация жюри)

Обязательно (P0): R0 (минимум), R2 (подбор, план, заявка, передача), R3 (потребность, заявка, получение), R6 (честный ИИ), R7 (один записанный прогон).

Можно сократить: R1 (членства, приглашения), R4 (отдельный контур переработки), R5 (аналитика — только блок на главной, без экрана), админ в мобильном клиенте, полный редизайн фаз C–F.

Не обещать: четыре роли с членствами, модерацию партий, живой ИИ без записанного прогона, оптимальность плана, определение состава по фото, CO₂, выручку платформы, платежи и партнёров без документов.

## 7. Основные риски

1. Миграция `users.role` → membership: ошибка backfill лишает пользователей доступа. Митигация: зеркало на переходе и проверка «никто не потерял доступ».
2. Дополнительный SELECT на каждый запрос (проверка прав из БД): замер p95.
3. Процессный rate limit не общий между воркерами. Для демо достаточно одного процесса.
4. Нет `created_by` в бизнес-таблицах: прошлых авторов не восстановить.
5. Нет живого провайдера ИИ и почты: часть E2E не проверяется.
6. Расхождение документации и кода сбивает оценку (см. раздел 0).

## 8. Решения, требующие владельца

Сведены из всех отчётов. Рекомендация — в скобках.

- **R-decision-1.** Минимум для покупателя во Flutter (каталог + потребность + заявка + получение; подбор для покупателя — P1).
- **R-decision-2.** Переработчик и `UNKNOWN_APPLICATION`: потребность с пустым списком применений для демо (отдельную роль не вводить).
- **R-decision-3.** Организация — продавец и покупатель одновременно: нет (два аккаунта, ограничение зафиксировать).
- **R-decision-4.** Самозаявленный `activity_type=recycler`: оставить с пометкой в UI.
- **R-decision-5.** Отмена `confirmed`-резерва покупателем: нет, только через продавца (покупатель отменяет `pending`).
- **R-decision-6.** Скрывать ли `min_kg` чужой потребности от продавца до сделки: да.
- **R-decision-7.** Передача рекомендации плана покупателю: вне платформы в MVP.
- **R-decision-8.** Несколько организаций и членства: нет в MVP (`CLAUDE.md` §4). Если да — первый этап без переключения: только membership и permissions.
- **R-decision-9.** Судьба `users.role`: зеркало на переходе, затем удаление (рекомендую).
- **R-decision-10.** Права MANAGER и MEMBER: приглашать можно, снимать нет (MANAGER); MEMBER без необратимых действий.
- **R-decision-11.** Admin вне `/admin/api/*` и модерация партий: только чтение и блокировка, модерации партий в MVP нет.
- **R-decision-12.** Вход по приглашению без аккаунта: обычная регистрация с отдельной организацией (без изменения `POST /auth/register`).
- **R-decision-13.** Демо-код `7777` и блокировка входа до подтверждения email: подтвердить (A23-12).
- **R-decision-14.** Почтовый провайдер для production: не выбран, без него реальная отправка не проверяется.
- **R-decision-15.** Порядок проверок (403 → 429 → 422 → 404 → 409) против `api.md` 19.1 (A20-6): утвердить фактический порядок.
- **R-decision-16.** ИИ для покупателя: вариант A (нет) по умолчанию.
- **R-decision-17.** Хранение токена: только в памяти (сейчас), без refresh и revoke в MVP.
- **R-decision-18.** Уведомления: счётчик «Ждут действия» на главной, без push и писем.
- **R-decision-19.** Срок хранения результатов анализа старых версий партии.
- **R-decision-20.** Права в организации: «право записи» флагом или любой enterprise (как сейчас).
