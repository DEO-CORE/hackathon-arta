## 1. Что обязательно для демо и что уже работает

Целевой сквозной сценарий: продавец создаёт партию с фото, ИИ-анализ с подтверждением, подбор покупателя с причинами, оптимизация с остатком, покупатель резервирует, продавец подтверждает и передаёт, покупатель подтверждает получение, аналитика разделяет прогноз и факт.

Условные обозначения: ГОТОВО = подтверждено запуском в документах QA; КОД = код/маршрут есть, тесты backend есть, но в UI и на устройстве не пройдено; НЕТ = не реализовано или не подтверждено.

| Шаг сценария | Backend | Flutter UI | Прогон на устройстве | Вердикт |
|---|---|---|---|---|
| Регистрация и вход | КОД (+ подтверждение email, `test_email_confirmation.py`) | есть (login, register, verify_email) | вход через «Заполнить» в демо-режиме | работает в демо; живой API не проходился |
| Создание партии, фото, хранение | КОД (`/materials`, images, локальный storage; Supabase не подтверждён, BLK-03) | есть | DEMO-01…03 PASS, но в ДЕМО-режиме без API | работает только на синтетическом локальном хранилище |

Честный итог: половина сценария (вход, партия, фото, подтверждение, публикация, симуляция ИИ) показана на устройстве в демо-режиме. Вторая половина (потребность, подбор, оптимизация, резерв, передача, получение, аналитика) существует только в backend и не имеет ни одного экрана. Для жюри это означает, что «работающий MVP» сейчас демонстрирует только предложение, а не сделку. Весь «ценностный» слой (оптимизация, остаток, деньги, факт) невидим.

Обязательное для демо (P0): всё из таблицы, что выше помечено КОД или НЕТ в строках от «Потребности покупателя» до «Аналитика», плюс один прогон на живом API (не в `USE_DEMO_DATA`).

## 2. Демо-имитация и то, чего показывать нельзя

Можно показывать с явной пометкой (баннер «Демо: синтетические данные»; для ИИ плашка «Симуляция» или «mock»):

- Синтетические организации, партии, потребности и цены. Фикстура помечена как синтетическая (`CLAUDE.md` §16). Цены и издержки на кг показывать как «предположение».
- Результат ИИ-анализа из фикстуры (`docs/fixtures/demo-analysis.json`) при потере сети или без ключа. Только с плашкой «Симуляция», уверенность словами, состав «Неизвестно».
- Заранее заведённые заявки/потребности «покупателя» как сидированные данные, а не как реальная активность.
- Фото из набора синтетических JPEG, а не реальные фото предприятий.
- Локальное хранилище вместо Supabase, если BLK-03 не снят: назвать это «локальное хранилище MVP».
- Роль второго участника, играемая тем же человеком на втором устройстве или втором входе. Говорить «две роли одного стенда», не «пилот с клиентом».

Показывать нельзя:

- Mock или фикстуру ИИ под видом живого провайдера. Нельзя выдавать режим mock за live (`CLAUDE.md` §6; `vision.py` уже различает режим, UI должен показывать его всегда).
- Определение состава, веса, прочности, безопасности по фото; проценты уверенности, не выведенные из модели.
- CO₂, тонны спасённого сырья, «сэкономлено сомов» без методики и источников (`CLAUDE.md` §10). Прогнозную экономию нельзя называть выручкой.
- Выручку, комиссию 5% как «доход ARTA», платежи, онлайн-оплату. Комиссия только как подпись «гипотеза».
- Любые заявленные пилоты, партнёрства, письма о намерениях, количество пользователей, если их нет в `claims-check.md` (его пока нет).
- Недействующие кнопки: «Пригласить в организацию», «Модерация», «Переработка» без экрана. Не показывать CTA, который ведёт в никуда (`CLAUDE.md` §14).
- Ручную правку БД, скрытый seed во время демо, подмену данных между прогонами.
- Нули и выдуманные метрики на Home. План редизайна сам запрещает показывать то, что API не вернул.
- Результат оптимизации со статусом `feasible` как «оптимальный» и сравнение с baseline, обещающее выигрыш на любом наборе.

## 3. Что откладывается после хакатона

| Блок | Решение | Причина |
|---|---|---|
| Администрирование и модерация (UI) | ОТЛОЖИТЬ. Допустимо показать один read-only список и существование `/admin` в слайде «дальше», не как функцию | Не входит в обязательный путь MVP (`CLAUDE.md` §2 «многоуровневая административная панель» исключена). Уже есть backend и тест `test_admin.py`, значит это актив, а не обязательство. Назначение admin только через `create_admin.py`, публичного пути нет, это нужно сохранить |
| Полноценные приглашения и членства организаций | ОТЛОЖИТЬ полностью | Требует новой модели (membership, роли внутри организации, токены приглашения, права на каждом запросе). Ломает инвариант «один пользователь, одна организация», на котором построены 100 backend-тестов и матрица авторизации. Риск: регрессия защиты владения. Демо не нуждается: достаточно одного пользователя на организацию |
| Четыре роли в коде (SUPPLIER, BUYER, RECYCLER, ADMIN) | ОТЛОЖИТЬ переименование и разделение. В питче называть «поставщик», «покупатель», «переработчик» как сегменты, в коде оставить enterprise/buyer(+recycler activity)/admin | Переименование ролей меняет enum БД, токены, OpenAPI, Flutter DTO и тесты, нулевая ценность для жюри |
| Переработчик как отдельный сценарий (подтверждение переработки как отдельный поток) | ОТЛОЖИТЬ как отдельный поток. Сохранить как показ: переработчик это покупатель с `activity_type=recycler`, использующий те же заявку/получение/`reuse-confirmation` | Причина отложить: единственное, что отличает переработку, это отдельный факт «переработано» и ёмкость в оптимизаторе (направление «переработка»). Направление «переработка» в оптимизации уже требуется (`CLAUDE.md` §8, три направления), и этого достаточно, чтобы жюри увидело три пути. Отдельный экран и роль не добавляют критериев оценки, но удваивают тестовую поверхность |
| Кыргызский язык, мобильные релизы, платежи, доставка | Отложено по `CLAUDE.md` | В исходном ТЗ вне MVP |
| Подтверждение переработки с реальным контролем качества, сертификаты | ОТЛОЖИТЬ | Нет данных и методики |

Оговорка про переработчика: если жюри спросит «а где переработка?», сильный ответ такой: направление «переработка» участвует в оптимизации как третий путь (ёмкость и ценность заданы синтетически), а отдельный контур подтверждения переработки это следующий этап. Это допустимо только если в оптимизаторе направление действительно отображается в плане; проверить прогоном до заявления.

## 4. Минимальный набор ролей для демо

Три роли и никак не больше:

1. Продавец (`enterprise`, в питче «поставщик»).
2. Покупатель (`buyer`), один аккаунт-мастерская, чтобы на экране была сделка.
3. Переработчик (`buyer` + `activity_type=recycler`) только как строка в подборе/плане («получатель: переработчик»), без отдельного входа и экранов. Если времени мало, второй вход не делать.

Админ в демо не логинится.

Экраны (минимум, с источником состояния):

Продавец: вход; Главная (две цифры реальных данных, без нулей-плейсхолдеров); каталог своих партий; создание партии с фото; карточка партии с публикацией; экран ИИ-анализа с «Предложено ИИ» и «Подтверждено вами»; экран подбора (список покупателей, score, причины, возможный объём); экран плана оптимизации (три направления, ожидаемая ценность, остаток, baseline, статус solver, метка «ожидается»); входящие заявки (подтвердить резерв, передать, отклонить); аналитика (зарегистрировано, распределено, подтверждённое использование, выручка завершённых, прогноз отдельной полосой).

Покупатель: вход; каталог доступных партий (только опубликованные поля); форма потребности; подача заявки с количеством; мои заявки (получение подтвердить); подтверждение использования (одна кнопка).

Не делать в демо: профиль-редактор сверх существующего, админ-экраны, чат, фильтры сверх базовых, приглашения.

Приоритет редизайна: `arta-ui-redesign-plan.md` описывает 5 фаз визуальной работы (B…F). Для сроков это опасный соблазн: фазы C/D/E улучшают то, что уже работает (вход, каталог, карточка), а не закрывают отсутствующие экраны сделки. Визуальная полировка (градиент, hatch, плавающая навигация, laptop-rail) это P1/P2 и не должна опережать экраны подбора, плана и заявок. Из плана оставить для P0 только то, что требуется функционально: `AppStatTriplet` (свободно/зарезервировано/передано), `AiSuggestionCard`, `AppSuccessView`. Остальное (`AppBottomSheet`, laptop-раскладка, гладкие фоны, переименование «Удержано» в «Зарезервировано» без согласования) отложить. Риски R2/R5/R7 плана (навигация, `pumpAndSettle`, тесты форм) реально сломают 130 зелёных тестов.

## 5. Риски презентации: что жюри проверит и что будет провалом

Что жюри может проверить вопросами (из критериев: инновации и влияние 35, бизнес-модель 20, понимание проблемы 15, MVP 15, питч 15):

1. «Что делает ИИ такого, чего не сделает форма с чек-листом?» Ответ не должен включать состав, вес, прочность. Подбор и распределение детерминированы, ИИ только предлагает признаки. Слайды не должны говорить «ИИ распределяет».
2. «Это живой ИИ или mock?» Должен быть честный ответ и видимая плашка режима. Сегодня живой провайдер BLOCKED (BLK-02).
3. «Откуда цифры?» (объём отходов, цена, 5%, «сколько сэкономит»). Любая цифра без пометки «предположение» или источника из `market-data*.md` засчитывается слабой. В реестре 29 допущений, ни одно не подтверждено интервью.
4. «Холодный старт: откуда взять покупателей?» Нужен конкретный план первых 5-10 партий и покупателей; без реальных контактов в публичных fixtures (`CLAUDE.md` §11).
5. «Готов ли покупатель платить 5%?» Это гипотеза; доказательства нет. Нужно сформулировать эксперимент, не результат.
6. «Покажите двойное резервирование.» Нужен записанный вывод теста гонки (QA-03). Без него защита не доказана.
7. «Покажите, что оптимизация лучше baseline.» Допустимо только на одном синтетическом fixture, с явной формулировкой, что это не обещание на любом наборе.
8. «Это работает с реальным сервером?» Сегодня прогон на устройстве шёл без API. Если ответ «нет», MVP-оценка падает.
9. «Чем не маркетплейс объявлений?» Ответ в ценности плана с остатком и подтверждённых фактах, не в самом каталоге.
10. «А как вы измеряете эффект на окружающую среду?» Единственный безопасный ответ: пока не заявляем CO₂, измеряем кг переданных и подтверждённо использованных.

Что будет провалом:

- Показать только создание партии, фото и «ИИ-анализ» и назвать это MVP: нет сделки, нет денег, нет оптимизации. Это именно текущее состояние UI.
- Любая сказанная цифра экономии, CO₂, количество партнёров или пользователей без записи в `claims-check.md`.
- Mock-ИИ, поданный как живой; процент уверенности; состав, «определённый по фото».
- Демо, требующее ручной правки БД или повторного запуска из-за состояния после предыдущего прогона (сброс демо-данных DEMO-10 NOT TESTED).
- Падение на живом API или сети во время демо без заранее отрепетированного fallback.
- Утверждение «четыре роли, организации с приглашениями, модерация» в слайдах при том, что этого нет в UI. Жюри попросит показать.
- Нулевые карточки на Home и мёртвые кнопки.
- Расхождение между питчем и задачником: если на слайде «работает», а в QA «NOT TESTED».

Незакрытые пункты QA, которые прямо влияют на демо: DEMO-08, DEMO-10, DEMO-11, AI-SIM-06, AI-SIM-07, DEV-01, DEV-02, DEV-05, живой API (BLK-03), живой ИИ (BLK-02). Дефекты DEV-06 (формат массы) и DEV-07 (автозаполнение показывает личные адреса Gmail) видны зрителю, DEV-07 это ещё и приватность на проекторе.

## 6. Рекомендуемый порядок работ (по приоритету, без дат)

P0, в таком порядке (каждая следующая строка зависит от предыдущей):

1. Прогон существующего backend против Flutter без демо-режима на одной БД: вход, партия, фото, подтверждение, публикация. Снимает главный риск «живой API не пройден». Зафиксировать результат в `docs/qa/`.
2. Определить и записать режим ИИ: либо ключ провайдера (BLK-02), либо явный demo/mock с фикстурой. Проверить подтверждение с экрана анализа (AI-SIM-06).
3. Экраны покупателя: потребность, каталог опубликованных полей, заявка.
4. Экраны продавца: подбор с причинами, план с остатком и baseline, входящие заявки, подтвердить/передать.
5. Покупатель: подтвердить получение; аналитика с раздельными полями (прогноз «ожидается», передано, подтверждено, выручка завершённых).
6. Идемпотентный seed с синтетическими данными и сбросом; запись команды в README только после реального запуска.
7. Записанный вывод гонки (QA-03) и E2E по `docs/demo.md` на свежей мигрированной БД (QA-04).
8. Создать `docs/demo.md`, `docs/pitch/pitch/claims-check.md`, питч-скрипты, только из того, что реально пройдено.

P1:

- Отдельное подтверждение использования и внутреннее использование в UI.
- Закрыть NOT TESTED из v2 (DEMO-08, DEMO-10, DEMO-11, DEV-01/02/05), DEV-06 и DEV-07.
- Минимальное визуальное: `AppStatTriplet`, `AiSuggestionCard`, `AppSuccessView`, плашка режима ИИ.

## 7. Пять рекомендаций по скоупу

1. Зафиксировать три роли в демо (продавец, покупатель-мастерская, переработчик как получатель в плане) и не вводить четыре роли с членствами до конца хакатона: модель «один пользователь, одна организация» сохраняет защиту и 100 backend-тестов.
2. Закрыть недостающую половину сделки в UI (потребность, подбор, план с остатком и baseline, заявка, подтверждение продавца, получение, аналитика) раньше любой визуальной работы; без этого MVP-балл ограничен демонстрацией «карточки с фото».
3. Один сквозной прогон Flutter → FastAPI → PostgreSQL без `USE_DEMO_DATA` с записанным результатом; всё, что не прошло, помечать «симуляция» или убирать из показа.
4. ИИ показывать только как предложение: плашка режима (mock или live) на каждом экране анализа, подтверждение человеком, подбор и распределение подписаны как детерминированные.
5. Все цифры и заявки в питче только из `claims-check.md`; 5% и экономия подписаны «гипотеза»; CO₂ не упоминать; админку и модерацию упомянуть единственной строкой «следующий этап».
