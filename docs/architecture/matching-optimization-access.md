Основание: `CLAUDE.md` §4, §5, §7, §8; `docs/optimization-contract.md` §3, §8; `docs/api.md` §5, §8–9, §10–13, §17.13–17.14, §18.8, §19.7, §21; `docs/decisions.md` D-08, D-11, D-12. ## 0. Роли и словарь

В системе три значения роли: `enterprise`, `buyer`, `admin`. Соответствие ролям из задачи:

| Роль в документе | В системе |
| --- | --- |
| SUPPLIER (продавец) | `role = enterprise` |
| BUYER (покупатель) | `role = buyer`, `activity_type` не `recycler` |
| RECYCLER (переработчик) | `role = buyer`, `organization.activity_type = recycler`. Отдельной роли нет |
| ADMIN | `role = admin`, создаётся только консолью (`app.create_admin`) |

Один пользователь принадлежит одной организации (упрощение MVP). Для чужого скрытого объекта возвращается 404, для известного, но запрещённого по роли действия 403.

## 1. Подбор (matching)

Общая функция совместимости и версия правил: одна на matching и оптимизатор (D-04). Hard-фильтры (тип, состояние, применение, исчерпанный спрос, невозможный минимальный объём, цена и бюджет, явная география) важнее score. Score 0–100: город 30, применение 30, покрытие 40 (`match-rules-v1`).

### 1.1 Продавец
- Запрашивает подбор для своей партии: `POST /ai/match {material_id, limit}`. Только владелец, только подтверждённые актуальные характеристики (иначе 409 `PRECONDITION_FAILED`). Чужая партия 404.
- Видит: `score`, `components`, `reasons`, `possible_kg`, `rules_version`, `excluded` с кодами причин, название организации потребности, город.
- Не видит: бюджет покупателя, контакты (api.md 17.13 Q3).

### 1.2 Покупатель
- Видит каталог опубликованных партий: `GET /materials` возвращает `MaterialPublicOut` для статусов `available`/`partially_allocated` при `available_kg > 0`. Скрыты: `held_kg`, `transferred_kg`, `internally_used_kg`, `total_kg`, `confirmed_by`, контакты, черновики, AI-предложения.
- Подбор «партии под мою потребность» с score, компонентами и версией правил в API сейчас НЕТ. `POST /ai/match` закрыт для buyer (403), `/ai/*` только enterprise. Что покупатель видит сейчас: каталог и свои потребности. Нужен маршрут (раздел 6, решение владельца 1).
- Если такой маршрут будет добавлен, он отдаёт покупателю только: `material_id`, `score`, `components`, `reasons`, `possible_kg`, `rules_version`, причины исключения для его собственных потребностей. Чужие потребности и чужой спрос не раскрываются.

### 1.3 Переработчик
- Те же права и те же ограничения, что у покупателя (роль `buyer`).
- Различие только в данных: оптимизатор помечает направление пары как `recycling`, если организация потребности имеет `activity_type = recycler`, иначе `sale` (`optimizer.py`). Категории (`material_types`, `conditions`, `uses`) переработчик задаёт в своей потребности; фильтрация по ним общая, отдельных правил для переработчика нет.
- Отдельной ёмкости переработки у переработчика на платформе нет: «внешняя» переработка задаётся продавцом как `assumptions.recycling` (допущение продавца, не данные переработчика).

### 1.4 Кто видит чужие потребности и на каких условиях

| Поле потребности | Владелец-buyer | Любой enterprise (список) | Участник сделки (резерв confirmed и далее) | Admin |
| --- | --- | --- | --- | --- |
| типы, состояния, город, применения, `active` | да | да, только `active = true` и чужие | да | да (панель) |
| `remaining_demand_kg`, `max_kg` | да | да (в `RequirementPublic`) | да | да |
| `min_kg` | да | да по текущей реализации (см. замечание) | да | да |
| `budget_per_kg` | да | нет, ключ отсутствует | нет в `ReservationOut`; отдельно не раскрывается | да (панель) |
| контакты организации | да (свои) | нет | да, после `confirm` | да |

Замечание о расхождении. По задаче «минимальная партия видна только участникам сделки». Текущий код (`RequirementPublic`) отдаёт enterprise `min_kg`, `max_kg`, `remaining_demand_kg` всех активных чужих потребностей, и api.md 5/9.1 это допускает. Это решение владельца 2.

## 2. Оптимизация

- Запускает: только `enterprise` для своих партий: `POST /optimization/run` (1–20 партий, до 100 активных потребностей, лимит `OPTIMIZATION_TIMEOUT_SECONDS`, rate limit). Чужая партия 404; партия без актуального подтверждения 409 `PRECONDITION_FAILED`.
- Видит план: только организация-владелец через `GET /optimization/runs/{id}` (чужой 404). Покупатель и переработчик план не видят: он содержит чужие цены, расходы и допущения. Admin видит планы только в панели `GET /admin/api/records/plans` для модерации.
- Принимает или отклоняет предложение: в системе нет сущности «принятие плана». Продавец плана не «применяет» одной кнопкой (D-11, A17-16). Отклонить план = не действовать по нему; план остаётся сохранённым и помечается `is_stale`. Покупатель решает за себя: подать заявку или нет.
- План не меняет `available_kg`, статус партии, спрос потребности, не создаёт заявок и не удерживает массу (`label = "expected"`).
- Метки: `objective_kgs` и `allocations[].net_value_kgs` — прогноз. Внутреннее использование и переработка по допущениям продавца — оценка, не выручка. `status` `feasible` и `heuristic` не называются оптимумом.

### 2.1 Путь от плана до резерва (только через обычные защищённые операции)

1. Продавец запускает `POST /optimization/run`, получает рекомендацию: для каждого направления продажи указаны партия, `requirement_id`, кг, прогноз.
2. Продавец проверяет `is_stale`; при `true` пересчитывает.
3. Продавец сообщает рекомендацию покупателю вне платформы (контакты видны только после `confirm`, поэтому в MVP это публикация партии и публичный каталог). Автоматического уведомления нет.
4. Покупатель сам вызывает `POST /reservations` (`Idempotency-Key` обязателен): создаётся `pending`, запас не удерживается. Проверки: партия опубликована и не его, `quantity_kg <= available_kg`, цена известна (не подставляется нулём), для `requirement_id` соблюдены тип, состояние, `min_kg`, бюджет, применение.
5. Продавец вызывает `PATCH /reservations/{id} {action: confirm}`: атомарно блокируются `materials`, затем `buyer_requirements` (D-08), повторно проверяются остаток и спрос, масса переходит в `held_kg`. При нехватке 409 `INSUFFICIENT_STOCK` или `DEMAND_EXCEEDED` с `details.available_kg` (D-12).
6. Продавец `transfer`, покупатель `complete`; использование подтверждает отдельным `reuse-confirmation`.

Внутреннее использование: продавец выполняет отдельную операцию `POST /materials/{id}/internal-use` с проверкой массы под блокировкой; строка плана «внутреннее использование» ничего не списывает сама.

## 3. Резервы и заявки

| Шаг | Кто | Операция | Эффект на массу |
| --- | --- | --- | --- |
| Создать заявку | buyer / recycler | `POST /reservations` + `Idempotency-Key` | нет (`pending`) |
| Подтвердить | enterprise-продавец | `PATCH` `confirm` | `available -> held`, спрос потребности уменьшается |
| Отказать / отменить | продавец (причина обязательна) или покупатель своей заявки | `PATCH` `cancel` из `pending`/`confirmed` | `held -> available`, спрос возвращается |
| Передать | продавец | `PATCH` `transfer` | `held -> transferred`, создаётся `transaction`; недопередача возвращается в `available` |
| Подтвердить получение | покупатель | `PATCH` `complete` | выручка учитывается здесь |
| Подтвердить использование | покупатель | `POST /transactions/{id}/reuse-confirmation` | `impact_record`, сумма не больше переданного |

Переработчик действует по тем же правилам, что покупатель. Повтор того же действия возвращает текущее состояние без второй сделки. Произвольный PATCH статуса запрещён.

Что видит каждая сторона:
- Продавец: `GET /reservations` — заявки по своим партиям; своё название партии, количество, согласованную цену, статус, транзакцию; контакты покупателя только при статусе `confirmed`, `transferred`, `completed`.
- Покупатель/переработчик: заявки своей организации; контакты продавца при тех же статусах. В `pending` контактов нет у обеих сторон.
- Не видят: заявки других организаций (404), `held_kg`/`transferred_kg` партии у покупателя, чужие планы.
- Admin: через панель, только чтение и блокировка доступа; в резервах не участвует.

## 4. Экономические метрики

| Метрика | Кто видит | Источник |
| --- | --- | --- |
| Прогноз ценности (`forecast.expected_net_value_kgs`, `expected_remainder_kg`, `is_stale`) | enterprise (свой последний план) | `GET /analytics/summary`, `/optimization/runs/{id}` |
| Прогноз внутренней экономии | enterprise, отдельно от выручки | план, допущение продавца |
| Фактическая выручка `revenue_kgs` | enterprise (по своим `completed`) | сумма сделок `completed` |
| Расход покупателя `spent_kgs`, `received_kg`, `confirmed_reuse_kg` | buyer / recycler (свои) | сделки `transferred`/`completed` |
| Агрегаты по платформе | admin (панель) | `GET /admin/api/summary` |

Правила: прогноз, резерв, передача и внутренняя экономия не увеличивают `revenue_kgs`. Выручка возникает только при `complete`. Прогноз хранится и показывается отдельным блоком с меткой «ожидается». Покупатель не видит прогноз продавца. CO2 не вычисляется.

## 7. Проверки на гонки и устаревание

Тесты на отдельном PostgreSQL (CLAUDE.md §15):

1. Двойное резервирование: две независимые сессии одновременно выполняют `confirm` на заявки с суммой больше остатка. Ожидание: ровно одна успешна, вторая 409 `INSUFFICIENT_STOCK` с `details.available_kg`, `available_kg >= 0`, баланс `total = available + held + transferred + internally_used`.
2. Двойной спрос: два `confirm` по одной потребности на сумму больше `remaining_demand_kg`: одна 409 `DEMAND_EXCEEDED`; спрос не отрицателен. Порядок блокировок `materials`, затем `buyer_requirements` (D-08); проверка отсутствия взаимоблокировки при заявках на разные пары.
3. Идемпотентность: повтор `POST /reservations` с тем же ключом и payload даёт исходный ответ и одну запись; с другим payload 409 `IDEMPOTENCY_KEY_REUSED`; конкурентные повторы дают одну запись. Повторные `confirm`/`cancel`/`transfer`/`complete` не создают второй `transaction` и `impact_record`.
4. Устаревший план: после изменения `version` партии (PATCH характеристик, новое фото), `total_kg`, `remaining_demand_kg` или остатка (`snapshot` не совпадает) `GET /optimization/runs/{id}` возвращает `is_stale = true`, а план по-прежнему не меняет массу. Рекомендация в клиенте: пересчёт, кнопка действий по плану не показывается.
5. Отказ при изменении входов: после сброса подтверждения (изменение типа, состояния, города, массы, фото) `POST /ai/match` и `POST /optimization/run` дают 409 `PRECONDITION_FAILED`; `POST /reservations` по снятой с публикации/зарезервированной партии 404; партия с активными обязательствами не допускает изменения массы и характеристик (409 `ACTIVE_OBLIGATIONS`).
6. План не заменяет проверку: резерв по строке «устаревшего» плана при уже уменьшенном остатке отклоняется на `confirm` по свежему состоянию, а не по плану.
7. Ролевые проверки: buyer получает 403 на `/optimization/*` и `/ai/match`; enterprise получает 403 на `POST /reservations`; чужие `reservation_id`, `transaction_id`, `run_id`, `requirement_id` дают 404; в ответах enterprise нет `budget_per_kg`; контакты отсутствуют в `pending`.
8. Метрики: `revenue_kgs` не меняется после запуска плана, `confirm` и `transfer`; растёт только после `complete`; прогноз отображается отдельным блоком.

## 8. Главные правила (кратко)

1. План и matching только рекомендуют. Масса меняется только `confirm`/`transfer`/`internal-use` под блокировкой с повторной проверкой остатка и спроса.
2. Заявку создаёт только покупатель/переработчик, подтверждает и передаёт только продавец своей партии, получение подтверждает только покупатель.
3. Бюджет покупателя и коммерческие данные скрыты от продавца; контакты открываются обеим сторонам только после `confirm`.
4. Прогноз ценности виден только продавцу и никогда не входит в выручку; выручка возникает на `complete`.
5. Один набор hard-фильтров и одна версия правил (`match-rules-v1`) для matching и оптимизатора; любой запрос проверяет роль, организацию и владение вложенных ID.

## 9. Решения для владельца

1. Нужен ли покупателю/переработчику собственный подбор (`POST /buyer-requirements/{id}/matches`) в MVP? Без него «покупатель видит score и причины» не выполняется. Рекомендация: добавить, P1; при нехватке времени оставить каталог.
2. Скрывать ли `min_kg`, `max_kg`, `remaining_demand_kg` чужих потребностей от enterprise до сделки? Сейчас они видны (`RequirementPublic`); для скрытия надо убрать `min_kg` из публичной схемы, а matching продавца продолжит учитывать его на сервере. Рекомендация: убрать `min_kg`, оставить `remaining_demand_kg` как ориентир.
3. Как продавец сообщает покупателю о рекомендованной строке плана (платформенное приглашение или вне платформы)? В MVP нет уведомлений; принять «вне платформы» или добавить минимальное приглашение (новая сущность).
4. Нужна ли переработчику отдельная проверка организации (активность `recycler` задаётся при регистрации без модерации)? Это влияет на направление `recycling` в плане. Рекомендация: оставить самозаявление и пометить в UI.
5. Может ли покупатель отменять `confirmed` резерв без согласия продавца (сейчас да, допущение)? Это возвращает массу в `available` и спрос потребности. Рекомендация: только `pending`, а `confirmed` отменять запросом через продавца.
