# ARTA — права на ИИ-анализ по ролям

Статус: проектный документ (только документация, код и миграции не менялись). Дата: 2026-11-07.
Основа: `CLAUDE.md` §4, §6, §11; `docs/ai-schema.md` разделы 1–12; `docs/api.md` §5, §10, §17.9, §22; `docs/decisions.md` D-07, D-11.
Где документ расходится с `api.md`, действует `api.md`, пока владелец не примет решение (раздел 7).

## 0. Соответствие ролей

В контракте ролей регистрации две: `enterprise` и `buyer` (+ служебная `admin`). Названия из задачи сопоставляются так:

| Роль в задаче | Что это в ARTA |
| --- | --- |
| SUPPLIER | `enterprise` (предприятие/мастерская, владелец партии) |
| BUYER | `buyer`, `activity_type` не `recycler` |
| RECYCLER | `buyer` с `organizations.activity_type = recycler`; отдельной роли нет (CLAUDE.md §4) |
| ADMIN | `admin`, создаётся только консолью `app.create_admin` |
| Аноним | запрос без валидного Bearer-токена |

Допущение MVP: один пользователь — одна организация, внутриорганизационных ролей и «права записи» отдельно от роли `enterprise` в модели нет. Поэтому «член организации с правом записи» сейчас означает: активный пользователь роли `enterprise`, чей `organization_id` равен владельцу партии. Если появятся несколько пользователей на организацию, правило не меняется, но потребуется флаг права записи (решение 5).

## 1. Кто что может

### 1.1 Запрос анализа
Только `enterprise` из организации-владельца партии, и только по своей партии (`POST /ai/analyze`). Проверяются: роль, организация, владение `material_id`, наличие фото (иначе 409 `NO_IMAGES`), лимит 429. Клиент не передаёт фото, ключи, URL и `input_version`: сервер берёт сохранённые фото по object key и читает `materials.version` сам.

### 1.2 Просмотр результата
`GET /ai/analyses/{id}`: только `enterprise` организации-владельца партии. Чужой анализ — 404 (не раскрываем существование). Остальные роли: buyer/recycler — 403, аноним — 401.

### 1.3 Подтверждение характеристик
Подтверждает только человек: `enterprise` организации-владельца через `POST /materials/{id}/confirm` с `version` и необязательным `analysis_id`. Сервер никогда не копирует значения из `validated_result` в поля партии; значения вводит человек через `PATCH`. Анализ принимается как основание, только если он принадлежит этой партии и организации, `succeeded`, `input_version == material.version`, и `version` запроса актуален (иначе 409). Подтверждение возможно и без анализа.

### 1.4 «Предложения ИИ» и «подтверждённые факты» отдельно
Видит владелец (enterprise) на экране S06 и в карточке партии:
- блок «Предложение ИИ» — только из `AnalysisOut.result`, всегда с меткой, режимом (`live` / `mock` / `fallback`, для демо — «Демо»), устаревшие скрыты («Устарело»);
- блок «Подтверждено» — только поля партии, у которых есть `confirmed_at` / `confirmed_by` актуальной версии.
Matching, оптимизатор и публичная карточка читают только подтверждённые поля, никогда `validated_result`.

## 2. Покупатель и переработчик: чужая партия

Рекомендация (вариант A, по умолчанию, действует сейчас):
- BUYER и RECYCLER не имеют доступа к `/ai/*` вообще (403). Результат анализа и «предложения ИИ» по чужой партии им не показываются.
- В опубликованной карточке (`MaterialPublicOut`) они видят только подтверждённые человеком характеристики: тип, состояние, город, масса, подтверждённый состав (если указан), фото по короткоживущим ссылкам. Состав «неизвестен» показывается как «Не указан», не как догадка.
- Покупатель не должен узнавать, был ли у партии ИИ-анализ, какой провайдер и режим.

Вариант B (не рекомендуется для MVP, решение владельца): показывать в публичной карточке отдельный блок «Визуальные признаки (предложение ИИ, не проверено)» — только `visual_features` (цвет/рисунок/фактура) актуального и подтверждённого владельцем анализа, без `reuse_options`, `notes`, провайдера и без каких-либо оценок. Риск: покупатель воспримет предположение как характеристику товара; нужна явная метка и согласие владельца партии. Для переработчика отличий нет (он `buyer`).

## 3. Администратор

Принцип: мониторинг, а не чтение содержимого. Уже реализовано: `GET /admin/api/records/analyses` отдаёт поля `id`, `material_id`, `input_version`, `status`, `provider`, `model`, `mode`, `error_code`, `created_at`. Это минимальный набор, его достаточно для разбора сбоев и оценки нагрузки.

Администратор НЕ видит:
- `validated_result` и любое содержимое результата (цвет, рисунок, `reuse_options`, `notes`);
- фото, object keys, подписанные ссылки (для admin они не выдаются; `GET` фото для admin не определён);
- payload, отправленный провайдеру, и сырой ответ провайдера (они не хранятся);
- контакты организаций рядом с анализом (запись анализа содержит только `material_id`; присоединять контакты в этом разрезе нельзя).

Дополнительно допустимо без нарушения принципов (если понадобится): агрегаты по `status`/`error_code`/`mode` за период, число попыток (`attempts`), длительность. Администратор не подтверждает характеристики и не запускает анализ от имени организации. Доступ admin к анализам логируется (`request_id`, user id, ресурс), без содержимого.

## 4. Правила, которые нельзя нарушить

1. ИИ не подтверждает характеристики и анализ. `confirmed_at` / `confirmed_by` заполняет только эндпоинт подтверждения по запросу человека. Успешный анализ оставляет подтверждённые поля партии неизменными.
2. ИИ не пишет в остатки, резервы, аллокации, транзакции, impact. Модуль анализа пишет только свою строку `ai_analyses` (узкий интерфейс job-сервиса), не имеет инструментов записи, SQL, секретов и URL для скачивания; в запросе провайдеру нет tool/function-определений.
3. Предложения не выдаются как проверенные состав, вес, прочность, безопасность, химические свойства; в схеме для них нет полей (`extra="forbid"`), неизвестное — `null` / `unknown`. Цен, спроса и CO2 в ответах и промптах нет. `requires_confirmation` всегда `true`.
4. Фото и текст — недоверенные данные. Инструкции внутри них не исполняются; провайдеру уходят только байты фото из хранилища по ключам этой партии и enum-значения; контакты, e-mail, названия организаций, UUID, ключи, подписанные URL не отправляются. Не логируются ключи API, подписанные ссылки, байты фото, полный payload.
5. Доступ проверяется на сервере на каждом запросе (роль, организация, владение, вложенный `analysis_id`/`material_id`); чужой объект — 404. Сбой ИИ не блокирует каталог, ручной ввод и подтверждение. Устаревший анализ (`input_version != version`) не может подтвердить новую версию.

## 6. Эндпоинты

Уже есть в контракте и реализации (`backend/app/api/planning.py`, `materials.py`, `admin.py`):
- `POST /ai/analyze` — 202, enterprise-владелец.
- `GET /ai/analyses/{id}` — enterprise-владелец, чужой 404.
- `POST /materials/{id}/confirm` — человек, с проверкой `version` и `analysis_id`.
- `POST /ai/match` — детерминированный, не использует ИИ-результат.
- `GET /admin/api/records/analyses` — метаданные для admin.

Нужны или стоит добавить (только список, без реализации):
- `GET /materials/{id}/analyses` — список анализов своей партии (последний и история) для экрана S06; сейчас клиент знает только `analysis_id` из 202.
- Явная проверка 403 (не 404) для `buyer` и `admin` на `/ai/*` и тест-матрица на каждую роль и аноним (401).
- Запись аудита доступа admin к `analyses` (без содержимого).
- Агрегированный мониторинг для admin (`/admin/api/summary`: счётчики по `status`/`error_code`/`mode`) — по необходимости.
- Только при варианте B (решение 2): поле `ai_visual_features` в `MaterialPublicOut` (и флаг владельца «показывать покупателям»).
- Только при решении 5: проверка права записи в организации в зависимостях доступа (сейчас её нет).

## 7. Решения для владельца

1. Видимость для покупателя и переработчика: вариант A (ничего из ИИ, только подтверждённые факты) или вариант B (блок `visual_features` с меткой «предложение ИИ, не проверено»). Рекомендация: A.
2. Если B: включается ли он по согласию владельца партии (флаг на партии) или для всех опубликованных партий; показывать ли режим `mock` / `fallback` покупателю (рекомендация: никогда не показывать демо-результат покупателю).
3. Права admin: достаточно метаданных (рекомендация) или нужна модерация содержимого по жалобе (тогда отдельный аудируемый доступ с фиксацией причины, без контактов).
4. Хранение истории: сколько времени хранить `validated_result` и записи анализов старых версий партии (рекомендация: срок и автоочистка, решает владелец с учётом приватности).
5. Права в организации: оставить «один пользователь — одна организация» (любой `enterprise` пользователь = право записи) или ввести внутриорганизационную роль/флаг «право записи» до публикации MVP.
