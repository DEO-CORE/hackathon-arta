## 1. Четыре роли

Соответствие названий: SUPPLIER = `enterprise` (в API и БД), BUYER = `buyer`, RECYCLER = `buyer` + `organization.activity_type = recycler` (CLAUDE.md §4, `api.md` 1.1), ADMIN = `admin`. Один пользователь принадлежит одной организации (упрощение MVP, CLAUDE.md §4). Публичная регистрация принимает только `enterprise` и `buyer`.

### 1.1 SUPPLIER (текстильное предприятие)

| Аспект | Содержание | Метка |
|---|---|---|
| Бизнес-ценность | Единственный источник предложения; ARTA фиксирует комиссию 5% от завершённой продажи | Допущение A-08 (CLAUDE.md §2: гипотеза для питча, не платёжный модуль) |
| Боль | Остатки лежат, выбрасываются или продаются неформально; не знают, кто купит; хранение и вывоз стоят денег | A-01, A-02, A-03, A-04: все assumption или to-validate, источников нет |
| Контекст рынка | Официально ~200 предприятий отрасли (MD-04, secondary); оценка правительства ~3 000, вероятно с неформальным сектором (MD-10, to-validate). Объём отходов Бишкека 50-80 т/сут (MD-15, to-validate, оценки расходятся). Единственный известный переработчик берёт ~3 т/сут от 40+ цехов и ~100 поставщиков по контрактам (MD-18, MD-20, secondary): у части поставщиков выход уже есть | Секторные данные секондари; значимость для ARTA: A-22, A-24 |
| Что важно для демо | Весь путь без ручных правок БД: партия, фото, AI-предложение, подтверждение человеком, публикация, matching, план с остатком и baseline, подтверждение резерва и передачи, внутреннее использование отдельно от передачи | CLAUDE.md §16 |

### 1.2 BUYER (мастерская, малый производитель, перепродавец)

| Аспект | Содержание | Метка |
|---|---|---|
| Бизнес-ценность | Создаёт спрос; без покупателей matching пуст, комиссия не возникает | Допущение A-18 (cold start) |
| Боль | Трудно найти дешёвую ткань нужного типа и размера | A-09 assumption. Контр-фактор: дешёвая импортная ткань может обесценивать обрезки (A-27, to-validate, MD-55, MD-56) |
| Что важно для демо | Опубликованная партия видна; потребность создана; заявка с `Idempotency-Key`; подтверждение получения; контакты видны только после `confirmed` | CLAUDE.md §4, `api.md` 3.10 |

### 1.3 RECYCLER (переработчик)

| Аспект | Содержание | Метка |
|---|---|---|
| Бизнес-ценность | Покупатель последней инстанции для остатка, который solver не может продать мастерским (направление `recycling`) | Допущение A-13 |
| Боль | Нужен стабильный собранный поток | A-11 assumption; число переработчиков не установлено (A-12 to-validate). Известный игрок уже работает с контрактными поставщиками (A-22) |
| Позиционирование | ARTA не первая точка переработки; говорить так нельзя (A-22) | Проверено документально (secondary) |
| Что важно для демо | Один переработчик получает остаток после плана; видно, что остаток не пропадает | Допущение: на демо это синтетический организационный профиль |

### 1.4 ADMIN (модератор)

| Аспект | Содержание | Метка |
|---|---|---|
| Бизнес-ценность | Нулевая прямая выручка; снижает риск злоупотреблений, нужен для поддержки и ручного matching в холодном старте | Допущение |
| Боль | Нужно отключить спам-аккаунт, посмотреть записи при споре | Допущение, интервью нет |
| Что важно для демо | Не нужен в основном сценарии. Показать «вход админа создаётся только консолью» как довод по безопасности. Не рекламировать модерацию контента: кода модерации партий нет (см. раздел 4) | CLAUDE.md §2: многоуровневая админка вне объёма |

## 2. Жизненный цикл по ролям

Общая часть (Проверено в коде: `frontend/lib/features/auth`, `backend/app/api/auth.py`, `frontend/lib/core/session/session.dart`).

Регистрация и вход (общие переходы):

| Состояние | Событие | Следующее состояние | Ошибки |
|---|---|---|---|
| Аноним | Открыть приложение | `/login` (guard) | |
| Аноним | «Регистрация» | форма: роль (Предприятие / Покупатель), email, пароль >= 10, организация, город, вид деятельности | 409 `EMAIL_ALREADY_REGISTERED`, 422 по полям, 429 |
| Зарегистрирован | 201 | `/verify-email`, код на email | 503 `EMAIL_DELIVERY_UNAVAILABLE`, если почта не настроена вне demo |
| Ожидает подтверждения | Код верный | подтверждён, затем обычный вход | 409 `INVALID_CODE`, `CODE_EXPIRED`, 429 |
| Подтверждён | Вход | токен в памяти приложения, `/` | 401 `INVALID_CREDENTIALS`, 403 `EMAIL_NOT_CONFIRMED`, 403 `ACCOUNT_DISABLED` |
| Авторизован | Выход (меню на главной) | локальная очистка сессии; на сервере нет revoke | |
| Авторизован | 401 от API | `expired = true`, возврат на вход с сообщением | |

Выбор роли делается один раз при регистрации и не меняется (смены роли в API нет, `PATCH /organizations/me` меняет `activity_type`, но не роль). Организация всегда создаётся новая вместе с пользователем (присоединиться к существующей нельзя, `api.md` 6.1).

### 2.1 SUPPLIER

| Этап | Описание |
|---|---|
| Онбординг | Виды деятельности в форме: `garment_factory`, `workshop`, `other`. `recycler` для enterprise запрещён сервером (422, A20-1) |
| Главный экран | Приветствие, карточка «Следующий шаг» (черновик, которому чего-то не хватает, иначе последняя партия), горизонтальный список до 10 партий, нижняя навигация: Главная, Партии, Организация |
| Основные действия | Создать партию (4 шага) и фото; подтвердить характеристики; запустить AI-анализ; опубликовать; matching и план; подтвердить, передать или отменить резерв; внутреннее использование |
| Второстепенные | Редактировать, архивировать, профиль организации, аналитика |
| Пустые состояния | «Партий пока нет. Добавьте первую.» + «Создать партию»; фильтр без результатов + «Сбросить фильтры» |
| Ошибочные состояния | 409 `VERSION_CONFLICT` (баннер «Обновить данные»), `ACTIVE_OBLIGATIONS`, `PUBLISH_REQUIREMENTS_NOT_MET` (чек-лист), 422 `UNSUPPORTED_IMAGE`, `IMAGE_LIMIT_REACHED`, 429; AI недоступен: ручной ввод работает |
| Уведомления | Сейчас нет. Минимум: счётчик «Ждут действия» на главной (pending-заявки к подтверждению, переданные ждут получения) из `GET /reservations?status=pending` без новых сервисов |
| Профиль | Название, город, вид деятельности, контакты (`GET/PATCH /organizations/me`) |

Переходы партии (владелец): `draft` -> (confirm, publish) -> `available` -> `partially_allocated` / `reserved` -> `completed`; `draft/available` -> `archived` (если `held_kg = 0`). Статус вычисляет сервер.

### 2.2 BUYER

| Этап | Описание |
|---|---|
| Онбординг | Виды деятельности в форме: `workshop`, `recycler` |
| Главный экран | Тот же экран, что у enterprise; при пустом списке кнопка «Открыть каталог»; навигация: Главная, Каталог, Организация. Блок «Ваши партии» для покупателя по смыслу неверен (показывает каталог) |
| Основные действия | Смотреть опубликованные партии; создать потребность; подать заявку; отменить свою; подтвердить получение; подтвердить использование |
| Второстепенные | Фильтры каталога, профиль |
| Пустые состояния | «Пока нет опубликованных партий.» (без действия); нет потребностей: нужен текст «Создайте потребность, чтобы продавцы подобрали вам партии» (Допущение, макета нет) |
| Ошибочные состояния | 404 на чужой/неопубликованной партии: «Объект не найден или недоступен.»; `INSUFFICIENT_STOCK`, `DEMAND_EXCEEDED` при подтверждении продавцом, о чём покупателю нужно сообщить статусом |
| Уведомления | Сейчас нет. Минимум: на главной «Заявка подтверждена, контакты доступны» / «Передано, подтвердите получение» |
| Профиль | Те же поля организации; контакты видны контрагенту только после `confirmed` |

Переходы заявки: `pending` -> `confirmed` -> `transferred` -> `completed`; `pending/confirmed` -> `cancelled`. Подтверждает продавец, `complete` и `reuse-confirmation` — покупатель (`api.md` 5, 12.1).

### 2.3 RECYCLER (BUYER с `activity_type = recycler`)

Отличается от BUYER только организацией. Все пути BUYER те же.

| Этап | Описание |
|---|---|
| Онбординг | Выбор роли «Покупатель», затем вид деятельности «Переработчик» (`ActivityType.recycler` в `register_screen.dart`) |
| Главный экран | Тот же, что у BUYER; специфики нет (Проверено в коде) |
| Основные действия | Потребность с `uses = recycling_shredding`, крупный `max_kg`, широкий список типов; заявка на остаток |
| Особенность | Оптимизатор использует признак `recycler` организации потребности (`backend/app/services/optimizer.py:52`). Подтверждённого применения у партии пока нет, поэтому потребность с непустым `uses` получает `UNKNOWN_APPLICATION` и не принимается в резерв (`api.md` 21) |
| Пустые/ошибочные состояния, уведомления, профиль, сессия | Как у BUYER |

Следствие: сценарий «переработчик забирает остаток» на живом контуре заблокирован до решения в `api.md` 21 (поле подтверждённых применений у партии) либо потребность переработчика создаётся с пустым `uses` (любое применение). Это нужно показать владельцу как решение 1.

### 2.4 ADMIN

## 3. Подтверждение, version, идемпотентность

| Операция | Роль | Подтверждение пользователем в UI | `version` | Идемпотентность |
|---|---|---|---|---|
| Регистрация | аноним | нет | нет | повтор email -> 409; лимит 429 |
| Подтверждение email | аноним | код из письма | нет | повтор с верным кодом для подтверждённого -> 200 (A23-9) |
| PATCH партии | enterprise | нет | обязательно, 409 `VERSION_CONFLICT` | нет ключа; конфликт по version |
| Подтверждение характеристик (`/confirm`) | enterprise | да, человек, AI сам не подтверждает | обязательно; опционально `analysis_id` с `input_version` | повтор для текущей версии -> 200 |
| Публикация | enterprise | подтверждающий чек-лист | обязательно | повтор на опубликованной -> 200 (19.3) |
| Архивация | enterprise | диалог «Архивировать партию?» | обязательно | `held_kg = 0`, иначе `ACTIVE_OBLIGATIONS` |
| Загрузка фото | enterprise | нет | меняет version, возвращает новую | клиентский ключ для фото в работе (LC-02) |
| AI-анализ | enterprise | результат — только предложение | `input_version` | тот же input_version при активной задаче -> тот же `analysis_id` |
| Внутреннее использование | enterprise | да (необратимое списание), рекомендовано | нет | `Idempotency-Key` обязателен |
| Запуск плана | enterprise | нет, план — рекомендация | снимок версий, `is_stale` | нет |
| Создание заявки | buyer | да | нет | `Idempotency-Key` обязателен |
| confirm / cancel / transfer / complete заявки | по роли (см. раздел 2) | да для cancel и confirm | нет | ключ допустим, повтор безопасен и без него; SELECT FOR UPDATE, 409 при гонке |
| Подтверждение использования | buyer | да | нет | `Idempotency-Key` обязателен; сумма не больше переданного |
| Отключение пользователя | admin | да (рекомендуется) | нет | повтор безопасен по смыслу (Допущение) |
| Потребность (POST/PATCH) | buyer | нет | поля version нет, последняя запись побеждает | нет |
