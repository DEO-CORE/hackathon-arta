# ARTA: план API для мультиролевой модели

Статус: **проект, не реализован**. Дата: 2026-11-07. Код, миграции и `docs/api.md` не менялись; перед реализацией каждый пункт переносится в `docs/api.md` в том же изменении, что и код (правило проекта).
Права: `rbac-permissions.md`. Таблицы: `organization-membership.md`.

## 1. Сквозные правила

- Формат ошибки, пагинация, decimal-строки, `extra=forbid` — как в `api.md` 1.x. Новые поля ответов только добавляются.
- Контекст запроса: `user` (из токена) + `active_org` (claim `org` либо `default_organization_id`) + `membership` + `permissions`. Зависимость `require_permission("materials:publish")` заменяет `require_roles(...)`; порядок проверок: 401 -> 429 -> 403 (нет права, **до** обращения к ресурсу) -> 404 -> 422 -> блокировка -> 409.
- **Правило раскрытия существования (403 vs 404):**
  1. Нет права на *класс* действия у активной организации/роли -> 403 `FORBIDDEN`, одинаковый ответ для существующего, чужого и несуществующего объекта.
  2. Право есть, но объект не принадлежит активной организации, не существует, скрыт или id неверный -> 404 `NOT_FOUND` (одинаковый ответ).
  3. Объект собственной организации, право есть, но состояние запрещает -> 409.
  4. Право есть, но объект виден роли только частично -> публичный DTO (как `MaterialPublicOut`).
- Новые коды ошибок (добавить в `api.md` 1.2): `MEMBERSHIP_INACTIVE` (403), `ORGANIZATION_SELECTION_REQUIRED` (409), `LAST_OWNER` (409), `INVITATION_INVALID` не вводится: недействительное приглашение = 404 `NOT_FOUND`.
- Идемпотентность новых операций: см. по каждому маршруту. Область `(user_id, operation, key)`, `operation` включает id активной организации.
- Версия (`version`): у членства; у профиля организации версии нет (как сейчас, `api.md` 4).

## 2. Новые эндпоинты

### 2.1 GET /auth/me

- Право: только аутентификация (без активной организации).
- Ответ 200: `{ "user": UserOut, "active_organization_id": uuid|null, "memberships": [ { "membership_id", "organization": { "id", "name", "city", "activity_type", "side" }, "role": "OWNER|MANAGER|MEMBER", "status": "active" } ] }`. Только `active` членства. `permissions[]` для активной организации — строки из реестра (клиент использует для показа действий, сервер всё равно проверяет).
- Ошибки: 401. Раскрытия нет: только собственные данные.
- Идемпотентность/конкурентность: чтение.

### 2.2 POST /auth/switch-organization

- Право: аутентификация.
- Запрос: `{ "organization_id": uuid }`. Ответ 200: `TokenOut` (новый токен с `org`).
- Ошибки: 401; 404 `NOT_FOUND` (организации нет **или** нет активного членства — один ответ); 403 `ACCOUNT_DISABLED`/`EMAIL_NOT_CONFIRMED` как у логина; 422; 429.
- Идемпотентность: безопасный повтор (каждый вызов выдаёт новый токен), ключ не нужен. Запись `org.switched` в аудит.
- Согласованность 403/404: чужая организация = 404, как чужие объекты.

### 2.3 GET /organizations/me/members

- Право `members:read`. Query: `page`, `page_size` (1..100, как `api.md` 1.3), `status` (по умолчанию `active`).
- Ответ 200: `Page[MemberOut]`, `MemberOut = { "membership_id", "user_id", "email", "role", "status", "version", "created_at" }`. `email` участника виден участникам той же организации; контакты организации и телефон не входят.
- Ошибки: 401, 403 (`MEMBERSHIP_INACTIVE` / нет права), 422.
- Раскрытие: список только активной организации; чужих членств не существует.

### 2.4 PATCH /organizations/me/members/{membership_id}

- Право `members:manage`. Запрос: `{ "version": int, "role"?: "OWNER|MANAGER|MEMBER", "status"?: "active|suspended" }`, хотя бы одно из двух; лишние поля — 422.
- Ответ 200: `MemberOut`.
- Ошибки: 401; 403 (нет права — до поиска); 404 (membership не принадлежит активной организации или неверный UUID); 409 `VERSION_CONFLICT` (`details.current_version`); 409 `LAST_OWNER` (понижение/блокировка единственного активного OWNER); 409 `PRECONDITION_FAILED` `reason=ADMIN_ACCOUNT_PROTECTED` для admin (не должно возникать, admin не бывает участником); 422.
- Конкурентность: блокировка `organizations` (FOR UPDATE), затем строки членства; сравнение `version`; инкремент атомарный. Тест на два одновременных понижения двух OWNER: допустим успех ровно одного.
- Идемпотентность: по состоянию (повтор с той же целевой ролью и актуальной `version` -> 409 `VERSION_CONFLICT`; повтор без изменений не создаёт записи аудита). Ключ не используется.
- Передача владения: через повышение другого участника до OWNER, затем понижение себя (Решение 7).

### 2.5 DELETE /organizations/me/members/{membership_id}

- Право `members:manage`. Мягкое удаление: `status='removed'`. Query/тело не требуются; заголовок `If-Match` не вводится, вместо него query `version` (обязателен, 422 при отсутствии).
- Ответ 204. Ошибки: 401, 403, 404, 409 `VERSION_CONFLICT`, 409 `LAST_OWNER`.
- Идемпотентность: повтор по уже `removed` -> 404 (не принадлежит активному набору) либо 204 при тех же параметрах; единое решение: **204 при повторе** на тот же membership в активной организации (удаление идемпотентно по состоянию), аудит повторно не пишется.

### 2.6 POST /organizations/me/members/leave

- Право: активное членство. Тело `{ "version": int }`. Ответ 204. Ошибки: 401, 403 `MEMBERSHIP_INACTIVE`, 409 `LAST_OWNER`, 409 `VERSION_CONFLICT`.
- Идемпотентность: повтор после выхода -> 403 `MEMBERSHIP_INACTIVE` (токен ещё несёт старую `org`); клиент вызывает `/auth/me`.

### 2.7 POST /organizations/me/invitations

- Право `members:invite`. Запрос: `{ "email": str, "role": "MANAGER|MEMBER" }`. Заголовок `Idempotency-Key` **обязателен** (повтор не отправляет второе письмо).
- Ответ 201: `{ "invitation_id", "email", "role", "status": "pending", "expires_at" }`; **токена и ссылки в ответе нет**.
- Ошибки: 401; 403 (нет права; MANAGER запрашивает роль `MANAGER` -> 403 `FORBIDDEN`, это ограничение класса действия, а не объекта); 422 (email, роль `OWNER` -> 422 `invalid_value`); 409 `IDEMPOTENCY_KEY_REUSED`; код `ALREADY_MEMBER` намеренно **не вводится**, чтобы не раскрывать членство email: приглашение существующего участника создаётся, при принятии роль не меняется (A-M-9); 429; 503 `EMAIL_DELIVERY_UNAVAILABLE`.
- Конкурентность: частичный unique `(organization_id, email) WHERE pending`; повторное приглашение того же email = отзыв прежнего + создание нового в одной транзакции.
- Раскрытие: ответ одинаков для существующего и несуществующего email.

### 2.8 GET /organizations/me/invitations

- Право `members:invite`. Ответ 200: `Page[InvitationOut]` (`invitation_id`, `email`, `role`, `status`, `expires_at`, `created_at`, без `token_hash`). Ошибки 401, 403, 422.

### 2.9 DELETE /organizations/me/invitations/{invitation_id}

- Право `members:invite`. Отзыв `pending`. Ответ 204. Ошибки: 401, 403, 404 (не из активной организации / неверный id), 409 `PRECONDITION_FAILED` `reason=INVITATION_NOT_PENDING` (уже принято). Повтор по отозванному -> 204 (идемпотентно по состоянию).

### 2.10 POST /invitations/accept

- Право: аутентификация и подтверждённый email; членство не требуется. Запрос: `{ "token": str }` (длина 32..128, `extra=forbid`). Ответ 200: `{ "membership": MemberOut-подобный, "organization": {id,name}, "access_token"?: ... }` — токен с `org` нового членства возвращается (избегает отдельного switch).
- Ошибки: 401; 403 `EMAIL_NOT_CONFIRMED`; **404 `NOT_FOUND` единый** для неизвестного, просроченного, использованного, отозванного токена и несовпадения email; 409 `PRECONDITION_FAILED` `reason=ADMIN_CANNOT_JOIN`; 422; 429 (по пользователю и IP).
- Идемпотентность: одноразовость на уровне БД. Повтор принятия *тем же пользователем* возвращает 404 (токен израсходован); клиент после сетевого сбоя вызывает `GET /auth/me`. Это сознательно: ключ не заменяет одноразовость токена.
- Конкурентность: условный UPDATE `status='pending'`; `UNIQUE(user_id, organization_id)`; при существующем `removed` членстве — реактивация, при `active` — приглашение расходуется, членство не дублируется, роль **не повышается и не понижается** автоматически (A-M-9).
- Раскрытие: единый 404 исключает перебор.

### 2.11 GET /audit-log

- Право `audit:read`. Query: `page`, `page_size`, `action`, `resource_type`, `from`, `to` (UTC), `actor_user_id`. Ответ 200: `Page[AuditOut]` (`id`, `occurred_at`, `actor_user_id`, `actor_membership_role`, `action`, `resource_type`, `resource_id`, `outcome`, `request_id`, `details` белого списка).
- Ошибки: 401, 403, 422. Только записи активной организации; фильтр по чужому `actor_user_id` просто даёт пустую страницу (не 404, не раскрывает).

## 5. Конкурентность и версии

- Операции с остатками (reservations, internal-use, publish/archive) сохраняют порядок блокировок D-08 и `version` партии; проверка членства/права выполняется **до** блокировок и не удерживает их (раздел 8 `organization-membership.md`).
- Управление участниками: `organizations` -> `organization_memberships`, не совмещается с блокировкой остатков.
- Переключение организации и приглашения: без `version`; защита уникальными ограничениями и условным UPDATE.

## 6. Тесты, которые должны появиться (план)

Unit: реестр прав и матрица; интеграционные на PostgreSQL: все пары роль × маршрут из раздела 3; понижение роли действует со следующего запроса с тем же токеном; последний OWNER; параллельное принятие одного приглашения (один успех); приглашение чужим email; два пользователя в разных организациях не видят данные друг друга (включая вложенные id фото, анализа, заявки, плана); admin не получает бизнес-права; регрессия: buyer publish/archive = 403, чтение чужой скрытой партии = 404.

## 7. Риски миграции существующих данных

1. **Backfill членств.** Для каждого `users` с ролью `enterprise`/`buyer`: `OWNER`, `active`, `invited_by NULL`. Ошибка backfill = пользователи теряют доступ (нет членства -> 403). Миграция должна быть идемпотентной (`ON CONFLICT DO NOTHING`) и сопровождаться проверочным запросом «пользователи без активного членства = 0».
2. **Существующие admin.** Организация «Администрация ARTA» формальная. Членство admin **не создаётся**; `/admin/api/*` не должны требовать членства. Если по ошибке потребовать — панель перестанет работать. Admin с `active=false`/без подтверждения остаётся как есть (0003 уже пометил всех подтверждёнными).
3. **Двойной источник истины** (`users.role`, `users.organization_id` и новые таблицы) на переходный период: рассинхронизация при ручных правках. Мера: один сервис; запись в оба места в одной транзакции; тест согласованности; удаление старых полей отдельной миграцией позже.
4. **Старые токены без `org`.** Остаются валидными до `exp` (60 минут); fallback на `default_organization_id`. Если у пользователя после внедрения несколько организаций и нет default — 409 `ORGANIZATION_SELECTION_REQUIRED` для старых токенов.
5. **Вычисление `organizations.side`** из `users.role` пользователей организации: у организаций с единственным пользователем однозначно; организации admin -> `platform`. Любые найденные организации с пользователями разных ролей (теоретически невозможно по `register`) — остановить миграцию с ошибкой, не угадывать.
6. **Нет `created_by` в бизнес-таблицах** (`materials`, `reservations`, `transactions`): исторические строки останутся без автора; в аудит прошлое не восстановить.
7. **Откат.** `downgrade` удаляет новые таблицы и столбцы `side`, `default_organization_id`; данные членств теряются, но `users.role/organization_id` не менялись, поэтому система возвращается к прежней работе. Запускать на копии БД, проверять `alembic upgrade head` на пустой и на заполненной БД. Ревизии сейчас: `0001` -> `c9c7720aa55d` -> `0003` (линейная); новая ревизия идёт после `0003`, создаётся одним агентом.
8. **Нагрузка на запрос:** дополнительный SELECT членства на каждый запрос; индекс `(user_id, status)` + UNIQUE покрывают; замер p95 обязателен (цель CLAUDE.md §15: p95 <= 1 с), без замера не заявлять.
9. **Rate limit процессный** (A20-10): лимиты приглашений и принятия не общие между воркерами; для нескольких инстансов нужно общее хранилище.
10. **Демо-данные:** отдельного seed-скрипта в репозитории не найдено (проверялось поиском по каталогу; поиск мог быть неполным). Если появятся demo-аккаунты, backfill их тоже должен покрыть.

## 8. Противоречия и устаревшие места в `docs/api.md`

1. §1.1: «Модерационных маршрутов в v1 нет» и §5: admin «не определено» — противоречит §22 (админ-панель и `/admin/api/*` реализованы) и `create_admin`. Матрица §5 и таблица §15 админ-маршруты не содержат.
2. §1.1 и `CLAUDE.md` §4: «один пользователь = одна организация (упрощение MVP)» — прямо противоречит плану. Отмена требует решения владельца (Решение 8), иначе вся мультиорганизационная часть не начинается; одно-организационное подмножество (членства + права без переключения) можно сделать отдельно.
3. §1.1: «для известного, но запрещённого действия по роли — 403» формулируется по *роли аккаунта*; план переводит на *право в активной организации*. Формулировку нужно обновить, поведение для текущих клиентов не меняется.
4. §19 («Не реализовано»), §20 («остальные маршруты не реализованы») и §21 (реализовано BE-04..BE-09) — разные моменты времени; §20 явно говорит, что устарело, но §19 и §17 остаются с «не реализовано». Фактическое состояние: §21.
5. §20 A20-8: `GET /materials/{id}/images/{image_id}/url` (8.5, в §15) в `backend/app/api` не найден; в сводке §15 он присутствует.

## Решения, требующие владельца

1. **Судьба `users.role`:** зеркало стороны организации на переходе и затем удаление, либо постоянно как платформенная роль. Влияет на размер миграции и тест согласованности.
2. **Может ли организация быть одновременно поставщиком и покупателем** (`side=both`). План: нет.
3. **Права MANAGER на участников:** приглашать/снимать MEMBER или только OWNER. План: приглашать MEMBER, не снимать.
4. **Права MEMBER:** подтверждение характеристик, запуск оптимизации, публикация, действия с резервами. План: MEMBER не делает необратимых и юридически значимых действий.
5. **Admin:** impersonation организаций и право на изменение данных организаций. План: нет, только чтение и блокировка.
6. **Регистрация приглашённого без аккаунта:** (а) `POST /auth/register` принимает `invitation_token` вместо данных организации; (б) обычная регистрация создаёт лишнюю организацию, затем принятие приглашения. План по умолчанию не выбран; (а) меняет контракт register.
7. **Несколько OWNER и передача владения:** разрешены ли несколько OWNER и нужна ли отдельная операция «передать владение». План: несколько OWNER разрешены, отдельной операции нет.
8. **Отмена упрощения «один пользователь = одна организация»** (`CLAUDE.md` §4, `api.md` 1.1) и срок/приоритет работ относительно P0 хакатона: мультиорганизационность не входит в обязательный путь MVP (§17), поэтому возможен вариант «только membership + permissions без переключения организаций» как первый этап.
