# Бэкенд ARTA

Серверная часть платформы для распределения текстильных остатков. Стек: Python 3.12+,
FastAPI, SQLAlchemy 2, PostgreSQL, Alembic и SciPy.

## Коротко для рассказа о проекте

Я сделал единый бэкенд ARTA для сайта на React и приложения на Flutter. Использовал слоистую архитектуру: маршруты принимают запросы, сервисы выполняют бизнес-логику, модели SQLAlchemy работают с PostgreSQL. Подключил регистрацию, личные профили покупателей, сессии, каталог, фотографии и полный цикл заявок. Добавил восстановление пароля через SMTP и адаптер OpenAI для анализа фото. Остатки и подтверждённое использование считает сервер; структуру базы обновляет Alembic.

## Архитектура

Путь запроса: **React / Flutter → REST API → сервисы → PostgreSQL**.

| Каталог | Назначение |
| --- | --- |
| `app/api/` | Маршруты HTTP, проверка доступа, вызов сервисов |
| `app/schemas/` | Проверка входных данных и формат ответов через Pydantic |
| `app/services/` | Бизнес-логика: сделки, остатки, аналитика, подбор и оптимизация |
| `app/models/` | SQLAlchemy-модели таблиц и ограничения данных |
| `app/db/` | Подключение к БД и управление сессиями |
| `app/core/` | Настройки, JWT, ошибки, ограничения частоты запросов |
| `app/integrations/` | Адаптеры внешних систем, включая хранилище фотографий |
| `migrations/` | Версионирование структуры БД через Alembic |
| `tests/` | Модульные и интеграционные тесты |

Это одно приложение с разделением ответственности по слоям. Синхронные маршруты FastAPI
выполняются в пуле потоков: работа с БД, блокировками, Pillow и Argon2 тоже синхронная.
Анализ фотографий запускается фоновой задачей. Оптимизатор SciPy рассчитывает рекомендации;
изменение реальных остатков выполняют только сервисы учёта.

## Что реализовано

- Регистрация, вход, роли, организации и личные профили покупателей без организации.
- HttpOnly-сессия сайта и восстановление пароля через SMTP с отзывом старых сессий.
- Публичный каталог для лендинга, подписанные ссылки на фото и подтверждённый счётчик.
- Партии материалов, фотографии, подтверждение характеристик, публикация и архивация.
- Потребности покупателей и подбор совместимых предложений по фиксированным правилам.
- Заявки: создание → подтверждение резерва → передача → получение; отмена до передачи.
- Учёт внутреннего использования и отдельные подтверждения использования покупателем.
- Аналитика своей организации: остатки, распределение, использование, выручка и прогноз.
- Сохранение планов распределения с ограничениями по массе, спросу и минимальному объёму.
- Фоновый AI-анализ с проверкой ответа, HTTP-адаптером и явно обозначенным деморежимом.

Swagger доступен по `/docs`, схема OpenAPI — по `/openapi.json`.
Миграция `4992ea002f67` продолжает `c9c7720aa55d`: добавляет личных покупателей, описание партии и одноразовые токены восстановления.
Приложение не создаёт таблицы автоматически при запуске: сначала нужно применить миграции.

## Быстрый запуск через Docker Compose

Выполняйте команды из каталога `backend/`:

```sh
cp .env.example .env
python -c 'import secrets; print("JWT_SECRET=" + secrets.token_hex(32)); print("POSTGRES_PASSWORD=" + secrets.token_hex(24))'
# Замените JWT_SECRET и POSTGRES_PASSWORD в .env сгенерированными значениями.
docker compose up --build
```

API: `http://localhost:8000`. Swagger: `http://localhost:8000/docs`.
Compose запускает PostgreSQL, применяет миграции и сохраняет БД и фотографии в именованных
томах Docker. Порт PostgreSQL не публикуется на хост.

## Запуск без Docker

Нужны Python 3.12+ и работающая PostgreSQL. Для БД используйте локаль UTF-8,
поддерживающую регистр кириллицы, например `C.UTF-8` или `en_US.UTF-8`.

```sh
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.lock
cp .env.example .env
# Укажите в .env реальные DATABASE_URL и JWT_SECRET (не менее 32 символов).
export DATABASE_URL=postgresql://user:password@localhost:5432/arta_dev
python -m alembic upgrade head
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

`DATABASE_URL` экспортируется отдельно, поскольку Alembic читает его из окружения.
Остальные настройки приложение загружает из `.env`.
Примеры переменных находятся в `.env.example`: `JWT_SECRET`, `CORS_ORIGINS`,
`STORAGE_LOCAL_DIR`, `ACCESS_TOKEN_MINUTES`, `RATE_LIMIT_*` и параметры AI.

Зависимости описаны в `pyproject.toml`. Зафиксированные версии — в `requirements.lock`
и `requirements-dev.lock`. Обновление через pip-tools:

```sh
pip-compile --strip-extras --output-file=requirements.lock pyproject.toml
pip-compile --strip-extras --extra dev --output-file=requirements-dev.lock pyproject.toml
```

## Настройка анализа фотографий

По умолчанию в разработке используется `VISION_PROVIDER=disabled`. Задача анализа завершается
ошибкой `PROVIDER_UNAVAILABLE`, а ручное подтверждение характеристик и операции со сделками
продолжают работать.

Для демонстрации задайте `VISION_PROVIDER=mock` и `DEMO_MODE=true`. Сервер вернёт подготовленный
синтетический пример с `mode=mock`. Это не реальный анализ фотографии.

Для подключения реального сервиса нужны `VISION_PROVIDER=http_json`, `VISION_ENDPOINT`,
`VISION_MODEL` и `VISION_API_KEY`. Реализован **протокол шлюза**: HTTPS-адрес принимает тело
`{model, images: [{mime_type, base64}], schema, instruction}` и ключ Bearer, а возвращает
JSON по схеме `VisionModelOutput`. Если выбранный AI-провайдер использует другой протокол,
нужен адаптер между ним и шлюзом. Готового подключения к конкретному поставщику пока нет.

Ответ проверяется на всех уровнях вложенности. Поля, которые нельзя достоверно определить
по фотографии, например состав и масса, не принимаются. Предложения AI хранятся отдельно
от подтверждённых характеристик. В режиме `APP_ENV=production` отсутствие настроенного
реального сервиса или включённый деморежим блокируют запуск.

Задачи сохраняются в БД до выполнения. Одновременно допускаются два обращения к провайдеру;
заданы таймауты и ограниченное число повторов. При перезапуске незавершённые задачи получают
статус `interrupted`.

**Запускайте один процесс Uvicorn и один экземпляр API.** Фоновые задачи и ограничения частоты
работают внутри процесса; распределённая очередь пока не реализована.
Фотографии хранятся локально в закрытом хранилище. Supabase Storage пока не подключён.

## React-лендинг, OpenAI и SMTP

Полное описание интеграции и запуска: [landing/INTEGRATION.md](../landing/INTEGRATION.md).
После запуска API в отдельном терминале выполните:

```sh
cd ../landing
npm ci
cp .env.example .env  # только при первом запуске
npm run dev -- --port 5173 --strictPort
```

Сайт: http://127.0.0.1:5173, Swagger: http://127.0.0.1:8000/docs, админка: http://127.0.0.1:8000/admin.
В серверном `.env` разрешите `http://127.0.0.1:5173,http://localhost:5173` в `CORS_ORIGINS`.

Для OpenAI задайте `VISION_PROVIDER=openai`, `VISION_MODEL` (модель с vision и Structured Outputs), `VISION_API_KEY`; `VISION_ENDPOINT` для этого провайдера не нужен.
Для писем задайте `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_SECURITY` и `LANDING_URL=http://127.0.0.1:5173`.
Примеры переменных перечислены в `.env.example`. Не перезаписывайте уже настроенный `.env`.
После изменения настроек перезапустите API. Пока ключ и SMTP не заполнены, ручные сценарии доступны, а внешние функции сообщают об отсутствии настройки. Реальная доставка писем и анализ требуют доступных учётных данных провайдеров.

Личный покупатель регистрируется с `profile: {name, city}`, без `organization`.
Для сайта используются `/auth/session`, `/auth/me`, `/auth/forgot-password`, `/auth/reset-password`;
Bearer-вход `/auth/login` для Flutter сохранён. Самостоятельной регистрации администратора нет.

## Правила учёта и принятые решения

- Порядок блокировок: партия → потребность → заявка → сделка. Подтверждение одновременно
  резервирует массу и спрос; отмена освобождает их; частичная передача возвращает разницу.
- Ключи идемпотентности защищают от повторной записи одной операции. Область ключа —
  пользователь и операция, срок повтора — 24 часа. Успехи и бизнес-ошибки 409 сохраняются
  вместе с результатом; остальные ошибки откатываются. Просроченный ключ обновляется
  при использовании; для длительной эксплуатации можно добавить периодическую очистку.
- Выручка учитывает только завершённые продажи. Передача, получение и использование —
  отдельные события. Внутреннее использование входит в подтверждённое использование,
  но показывается отдельно от распределённой массы.
- Для matching используется мобильный формат из `docs/api.md`: целочисленный `score`,
  `components.use` и `possible_kg`. Альтернативный формат дробных баллов из контракта
  оптимизации не публикуется как второй несовместимый ответ.
- У партии пока нет поля подтверждённых способов применения. Поэтому потребность с непустым
  `uses` не проходит подбор и резервирование: предложения AI не заменяют подтверждение.
  Пустой `uses` означает отсутствие предпочтений. Допускаются все семь значений справочника.
- Оценки внутреннего использования и переработки задаёт пользователь: это допущения
  о пригодности, ценности, расходах и общей ёмкости направления для выбранных партий.
  При неизвестной цене или расходах вариант исключается. Нулевые расходы нужно указать явно.
- SciPy распределяет целое число граммов с учётом минимальных объёмов, общего спроса и остатков.
  После расчёта ограничения проверяются через Decimal. Базовый план строится на тех же данных.
  Если solver не вернул допустимое решение, используется базовый план со статусом `heuristic`.
- План не изменяет запас или спрос. Он устаревает при изменении версии, остатка, статуса,
  подтверждения партии или снимка активных потребностей. Лимит расчёта — 20 партий и
  100 активных потребностей.
- Черновые и архивные партии нельзя списывать на внутреннее использование.
  Архивация отменяет ожидающие заявки с причиной `MATERIAL_ARCHIVED`.

## Тесты и проверки

Интеграционным тестам нужна отдельная одноразовая БД PostgreSQL с именем, оканчивающимся
на `_test`. Тесты выполняют откат и применение миграций и очищают таблицы между сценариями.
Не используйте БД с рабочими данными.

```sh
export TEST_DATABASE_URL=postgresql://user:password@localhost:5432/arta_test
python -m pytest
python -m ruff check .
python -m ruff format --check .
```

- `tests/integration/test_commerce.py`: полный цикл сделки, частичная передача, выручка,
  права доступа, повторные запросы, конкурентное резервирование и подтверждение использования.
- `tests/integration/test_planning.py`: подбор, расходы, устаревание планов, AI-подтверждение,
  изоляция данных и схемы OpenAPI.
- `tests/unit/test_optimizer_and_vision.py`: общий спрос, минимальные объёмы, дробная масса,
  проверка плана, резервный расчёт и валидация AI.

Результаты проверки 7 ноября 2026 года:

- **119 тестов прошли** на Python 3.14 и PostgreSQL 18.6 с локалью `C.UTF-8`.
- `ruff check`, `ruff format --check`, `git diff --check` прошли.
- `alembic check` подтвердил соответствие моделей миграциям; откат и применение проверены тестами.
- Совместимость зависимостей с Python 3.12 проверена пробным разрешением без установки.
- Docker и Compose не запускались: Docker отсутствовал в окружении проверки.
- Реальный AI-шлюз и Supabase не проверялись: настройки доступа не предоставлены.

## Текущее локальное окружение без Docker

Для запуска 7 ноября подготовлены PostgreSQL в `/tmp/arta-postgres`, её данные в
`/tmp/arta-pgdata` и БД `arta_dev` на `127.0.0.1:54329`. `.env` настроен на эту БД.
Это временное окружение: содержимое `/tmp` может удаляться при перезагрузке.
Для постоянной разработки используйте установленную PostgreSQL или Docker Compose.

Если PostgreSQL уже запущена, API можно повторно запустить из `backend/`:

```sh
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Для интерфейса в Firefox используйте `flutter run -d web-server`, как описано
в `frontend/README.md`.

## Собственная админка

Адрес: `http://localhost:8000/admin`. Интерфейс встроен в FastAPI, отдельная сборка не нужна.
Доступны сводка платформы, поиск и просмотр пользователей, организаций, партий, потребностей,
заявок, сделок, AI-анализов и планов. В карточке пользователя можно отключить или восстановить
доступ. Администраторов отключать через панель нельзя. Изменения доступа записываются в журнал
`arta.admin.audit`; пароль и токены в журнал не попадают.

Создание нового администратора из каталога `backend/`:

```sh
.venv/bin/python -m app.create_admin --email admin@example.com
```

Команда дважды запросит пароль, не показывая его на экране. Существующий аккаунт она не
изменяет. Публичная регистрация не позволяет назначить роль admin. Все маршруты `/admin/api/*`
проверяют роль на сервере; отключённый пользователь теряет доступ при следующем запросе.
Токен панели хранится только в памяти страницы: после обновления страницы нужно войти снова.
Остатки, сделки и прогнозы в панели доступны для просмотра; изменение баланса напрямую запрещено.
